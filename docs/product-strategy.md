# Property Concierge 상용화 방향과 구현 순서

Property Concierge는 사용자가 가져온 부동산의 가격·자금·위험·적합성과 다음 행동을 근거로 설명하는 의사결정 플랫폼을 목표로 한다. 장기적으로 거래 준비·협상·계약·잔금·등기까지 하나의 매수 케이스에 연결한다. 초기 출시 기준은 기능 개수가 아니라 **아파트 매물 하나를 등록했을 때 무엇을 판단할 수 있고 무엇이 미확인인지 끝까지 설명하는 것**이다.

사용자가 제시한 Decision Platform → Transaction OS 비전을 기준으로 정리했다. 아래 ‘계획’ 항목은 구현 완료를 뜻하지 않는다. 현재 상태는 2026년 10월 1일 저장소 코드를 기준으로 확인했다. 구현 위치와 다음 작업의 인수인계는 [프로젝트 인수인계](project-handoff.md)를 따른다. 모바일 앱은 현재 착수 범위에서 제외하고 이후 단계로 둔다.

## 기존 구현을 재사용할 부분

| 영역 | 현재 기반 | 보완할 부분 |
|---|---|---|
| 관심 매물 등록 | 주소 검색·도로명·지번·확인 건물명·선택 별칭, 링크·수동 입력·CSV, 사용자별 보관·출처·확인 시각 | 방향·입주일·전용 및 공급면적·중개업소·사진·메모 등 입력 확장, 개별 동·호와 실제 객체 매칭 |
| 매물 시간 관리 | `ImportedListing`, `ListingRevision`, `ListingObservation`, 원본 변경 재검토 | 최초 및 최근 관측·최신 성공·가격 변화 집계와 전용 타임라인, 광고 상태와 자료 최신성 분리 |
| 가격 분석 | 실거래 저장소, 유형별 AVM, 신뢰도·비교사례 수·매칭 수준 | 같은 면적·기간의 원문 근거, 충분한 평가 표본, 추정 불가와 낮은 신뢰도의 명확한 표시 |
| 자금 분석 | 화면·대화·케이스 시나리오, 취득 후 주택 수·비상자금 적용 통일, 후보별 저장 조건 복원 | 최신 금융·세금 규칙의 독립 검증과 실제 사례 입력 대조 |
| 권리 점검 | 사용자 PDF의 텍스트·규칙 기반 위험 신호, 업로드·판독 성공 분리, 자료 부족의 미확인 처리 | 문서 발급일·페이지·항목 단위 근거와 탐지 정확도 검증 |
| 의사결정 | `PurchaseCase`, `CaseProperty`, 다섯 판단 축·근거·기준일·누락 정보, 공통 기준의 요약·비교·다음 행동 | 실제 사례의 근거 대조, 입지와 생활 조건의 확인 가능한 자료 |
| 거래 준비 | 선택한 후보의 작업·일정·외부 대기·확인 결과 | 임장 기록·협상 제안과 응답·서류 재확인을 케이스에 연결 |
| 운영과 평가 | DB·Redis·작업 실행기 준비 점검, 백업, 운영 지표, 평가 도구 | 공개 서버·도메인 적용, 외부 감시·실메일·복원 검증, 실제 사용자 흐름 평가 |

이미 존재하는 모델을 이름만 바꿔 다시 만들지 않는다. 데이터가 연결되지 않은 새 기능을 늘리기 전에 같은 후보의 주소·가격·면적·자금 조건이 모든 화면과 도구에서 유지되는지 확인한다.

## 첫 출시 범위

아파트 매매와 현재 데이터가 검증된 지역을 우선 대상으로 한다. 다른 유형의 기존 분석 기능은 유지하되 유형·지역별 데이터와 검증 수준을 표시한다. 전국 모든 자산의 같은 수준의 분석이 가능하다고 설명하지 않는다.

첫 출시 흐름은 다음과 같다.

```text
관심 매물 URL 또는 수동 등록
  → 주소와 부동산 객체 확인
  → 매수 케이스와 후보 저장
  → 가격·자금·권리와 누락 정보 확인
  → 후보 비교와 선택·제외 이유 기록
  → 임장·은행 조회·서류 확인 등 다음 행동
  → 가격·상태 변경 시 재검토
```

URL을 열거나 추출하지 못하면 사용자가 확인한 값과 확인 시각을 직접 저장할 수 있어야 한다. 사용자 입력 호가, 국토부 실거래, AVM 추정가는 서로 다른 자료로 표시한다. 비공식 포털 수집 성공 여부가 이 흐름의 필수 조건이 되지 않게 한다.

## 가장 먼저 구현할 의사결정 결과

기존 후보 비교·요약 API 위에 아래 다섯 축의 공통 결과 계약과 화면을 추가했다. 새 계산 엔진을 만드는 단계가 아니라 저장된 근거·상태·다음 행동을 같은 기준으로 연결하는 첫 구현 단위다. 사용 경로와 정확한 검토 기준은 [후보별 의사결정 검토 기준](decision-assessment.md)을 따른다.

| 판단 축 | 확인할 내용 | 초기 표시 기준 |
|---|---|---|
| 적합성 | 예산·면적·연식·관심 지역·사용자가 명시한 생활 조건 | 확인한 조건만 비교하고 통근·학군·소음 자료가 없으면 미확인 |
| 가격성 | 희망가·실거래 비교·AVM 범위와 신뢰도 | 유효한 비교사례와 충분한 신뢰도가 있을 때만 가격 차이 해석 |
| 자금성 | 필요 현금·비상자금·월 상환액·부족액·대출 기준 | 입력 조건·계산 기준일과 함께 표시, 은행 승인과 구분 |
| 위험성 | 업로드 문서에서 발견한 위험 신호·확인하지 못한 항목 | 자료가 없거나 판독이 실패하면 안전으로 표시하지 않음 |
| 실행성 | 임장·은행 조회·서류 보완·재계산 등 다음 행동 | 기존 다음 행동 및 거래 준비 작업과 연결 |

각 결과에는 상태, 사용한 사실, 출처, 확인 시각, 계산 조건, 추정 여부, 누락 정보와 연결할 다음 행동을 포함한다. 상태는 확인 가능·주의·미확인·갱신 필요·오류를 구분한다. 전체 점수 하나나 자동 매수 결론으로 축약하지 않는다.

권리 원문 PDF는 현재 무저장 원칙을 유지한다. 문서 근거를 추가할 때는 사용자 소유 범위에서 분석 시각·문서 해시·페이지·필요한 최소 발췌의 보관 정책을 먼저 정하고, 원문 자동 영구 저장을 도입하지 않는다.

## 매물 객체와 시간 모델

물리적 부동산과 광고를 분리하는 방향은 유지한다. 초기에는 단지·건물·필지·개별 호의 식별 수준과 확인 출처를 먼저 정한다. 주소만 같은 광고를 같은 매물 또는 같은 호로 자동 합치지 않는다. 단지 수준으로만 확인되면 그 수준을 표시한다.

직접 등록에 [주소 기반 등록과 선택 별칭](address-based-listing.md)을 반영했다. 조회한 건물명·도로명·지번과 출처·조회 시각을 저장하고 이름 미확인은 주소로 표시한다. 별칭은 표시용이며 분석 이름을 대체하지 않는다. 이 연결은 건물·필지 수준이고 개별 호를 식별한 `Property` 기준정보 전체의 완료는 아니다.

`Property` 기준정보를 도입할 때 기존 `ImportedListing`에 선택적인 객체 연결을 추가하고 검증된 자료부터 이관한다. 사용자별 광고·메모·후보·원본 변경 이력의 접근 권한은 유지한다. 전국 주소를 미리 수집하거나 유형별 테이블을 모두 만든 뒤에 서비스를 시작할 필요는 없다. 유형별 상세 정보는 실제 입력과 분석 요구가 생긴 순서대로 추가한다.

시간 관리에서는 아래를 구분한다.

- 광고의 거래 상태: 사용자가 확인한 거래 가능·철회·완료·미확인.
- 자료의 상태: 최신·오래됨·수집 실패·페이지 미노출.
- 확인 수준: 사용자 확인·중개사 확인·공식자료 확인·계산·AI 추정.

페이지 미노출을 거래 완료로 바꾸지 않는다. ‘거래 완료’는 확인 주체·시각·근거가 있을 때 기록한다. 계획상의 추가 상태는 기존 상태와 호환되는 매핑 및 상태 변경 이벤트를 먼저 정의한 뒤 도입한다.

Listing Time Machine의 초기 결과는 최초 관측가격·현재 확인가격·관측 가격 변경 횟수·누적 변화율·마지막 확인 시각이다. 서비스가 처음 관측하기 전 기간은 알 수 없으므로 광고 최초 게시일이 확인되지 않았다면 **서비스 관측기간**으로 표시한다. 인하 이력은 협상 기록을 준비하는 근거가 될 수 있지만 실제 협상 가능성이나 매도자의 사정을 확정하지 않는다.

## 사용자 의사결정 기록

Buyer Decision Graph는 처음부터 별도 그래프 DB나 자동 학습 모델을 도입하지 않는다. 기존 케이스에 아래 기록을 구조화해 쌓는 것부터 시작한다.

- 후보를 선호하거나 제외한 이유와 사용자가 지정한 중요도.
- 임장일·체크리스트·사진·메모와 실제 확인 내용.
- 협상 제안가격·응답·확인 시각과 후속 행동.
- 같은 사용자의 조건 변경과 비교·선택 근거.

초기 추천은 사용자가 직접 지정한 조건을 적용한다. 반복되는 제외 이유에서 추정한 선호는 사용자에게 확인하고, 예산·생활 조건으로 조용히 확정하지 않는다. 충분한 기록과 별도 평가가 확보된 뒤 개인화 모델을 검토한다.

## 단계별 완료 기준

| 순서 | 개발 목표 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1 | 아파트 매수 의사결정 완성 | 등록 → 실제 분석 → 비교 → 선택·제외 → 다음 행동 → 새로고침 복원과 변경 재검토를 재현 가능하게 검증 |
| 2 | 근거와 매물 시간 관리 | 주요 판단을 원자료 또는 계산 조건으로 추적 가능, 확인 시각·실패·변경 이력을 구분 |
| 3 | 임장·협상·명시적 선호 기록 | 실제 사용자가 현장 기록과 검토 이유를 남기고 다시 비교에 활용 가능 |
| 4 | 주거 유형 확대와 모바일 검토 | 유형별 데이터·독립 정답셋·실패 처리가 확보됨. 모바일 웹으로 확인한 현장 수요를 앱 요구사항으로 정리 |
| 5 | 상업·업무·산업 및 토지 | 유형별 입력·NOI·Cap Rate·시설·용도지역 등 자료와 분석 검증이 확보된 유형부터 제공 |
| 6 | 매도자·중개사 공급 및 Marketplace | 공급자 식별·등록 검증·중복 광고 구분·상태 확인·대량 갱신 운영이 가능 |
| 7 | 매수·매도자 연결과 거래 지원 확대 | 본인·권한 확인, 연락·서류·일정의 책임 범위와 실제 거래 운영 절차가 검증됨 |

사용자가 제안한 모바일 앱은 유지하되, 독립 앱 착수는 임장·사진·오프라인·알림의 실제 사용 수요를 확인한 뒤 결정한다. 상업·산업·토지는 하나의 단계로 묶어 한꺼번에 완성하지 않는다. 자료와 검증이 준비된 유형별로 출시한다.

## 출시와 평가

소수의 실제 매수 검토 사용자를 대상으로 아파트 흐름부터 검증한다. 초기 파일럿 인원은 5~10명을 제안하며 현재 확보된 사용자가 있다는 뜻은 아니다. 공개 운영 전에는 준비된 운영 설정을 실제 서버·도메인에 적용하고 외부 접속·장애 감지·백업 복원·인증 복구까지 확인한다.

지표는 기능 개수 대신 등록한 매물의 주소 확인 가능 여부, 분석 완료 및 미추정 비율, 근거 추적 가능 비율, 누락 위험과 다음 행동의 정확성, 후보 비교·선택 이유 기록, 사용자 재방문과 실제 다음 행동 완료로 잡는다. 현재 운영의 단계별 사용자 집계를 같은 사용자군의 전환율로 해석하지 않으며 별도 집계 계약이 필요하다.

가격·자금·권리·다음 행동의 정답셋을 분리한다. 독립 수기 계산과 공식 자료 대조, 시간 기준을 지킨 AVM 평가, 문서의 위험 항목·페이지를 사람이 확인한 사례, 오류·미입력·변경·복원까지 포함한 브라우저 흐름을 함께 사용한다. 체크리스트 완료나 테스트 통과를 실제 거래 안전 또는 사용자 투자 성과로 설명하지 않는다.

공식 데이터 연결은 자료별 식별과 제공 범위를 확인하며 추가한다. [국토부 아파트 매매 실거래 API](https://www.data.go.kr/data/15126469/openapi.do)는 신고된 거래 자료이고, [건축HUB 건축물대장정보 API](https://www.data.go.kr/data/15134735/openapi.do)는 건축물대장의 속성정보를 제공한다. 이 자료가 광고 호가·현재 거래 가능 여부·개별 호의 완전한 동일성을 독립 검증해 주는 것은 아니다.

현재 자금 입력 기준 통일과 검증 기록은 [자금 분석 입력 기준](funding-consistency.md), 운영 조건은 [운영 안내](operations.md), 평가 범위는 [평가 안내](../evaluation/README.md)를 따른다. **후보별 다섯 판단 축과 근거를 모은 API 및 화면**을 첫 구현 단위로 반영했다. 다음은 실제 아파트 사례에서 주소·동일 객체 연결과 비교사례·권리 문서 근거를 보강하고 전체 흐름을 검증하는 작업이다. 이 화면 추가만으로 1단계 전체의 완료를 선언하지 않는다.
