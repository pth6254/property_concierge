# Property Concierge 프로젝트 인수인계

기준일: **2026-10-05**. 현재 제품 방향은 사용자가 가져온 매물의 가격·자금·권리와 미확인 사항을 검토하고, 후보 비교·사용자 선택·다음 행동을 지원하는 **부동산 Decision Platform**이다. 장기적으로 Transaction OS를 목표로 한다. 현재 작업은 웹의 아파트 매수 의사결정 기반 강화이며 **독립 모바일 앱은 나중에 진행한다**.

## 현재 반영한 범위

AVM은 공통 대상·자료 점검·방법 선택·결과 종류 계약(`PC-AVM-1.0-runtime-1`)을 연결했다.
아파트도 전용면적·개별 호실·단지명·주소와 최근 6개월 동일 단지 유사 면적 거래 5건 이상을 요구한다.
나머지 주거는 기준 보완 전 가격을 보류하고, 상가/업무는 입력 수익 시나리오, 토지는 공개자료만 제공한다.
공장/창고는 지원 보류다. 보고서와 후보 가격 축에 기준·보류 이유·다음 행동을 표시하고 저장 후 복원한다.
후보와 다른 주소·면적·유형·동호 결과의 연결을 거부하며 원본 변경 재검토를 유지한다.
전체 유형의 모델 정확도 검증이나 ML 운영 연결은 아니다. 상세 계약과 다음 작업은
[현재 실행 제한](features/decision.md#valuation-implementation)을 따른다.

저장소는 서비스 책임에 따라 `services/platform/`, `services/intelligence/`, `web/`,
`contracts/`, `infrastructure/`로 정리했다. 이전 루트의 서비스 구현 폴더는 이동했다.
실행은 `scripts/compose.sh` 또는 `compose.ps1`를 사용해 기존 프로젝트·데이터 볼륨을 유지한다.
경로·설치·검증 범위는 [저장소 구조](architecture.md#repository)를 따른다.

백엔드는 사용자 결정에 따라 Kotlin + Spring Boot의 저장·권한·거래 상태와 Python의 AI 분석으로 분리했다.
고정 수식의 자금·세금 계산은 Kotlin으로 이전했다. Python 시뮬레이션·챗봇·비교도 같은 내부 계산 계약을 호출한다.
이전된 회원·매물·케이스·거래 준비·분석 이력·작업 저장의 중복 Python SQL과 금융·세금 수식은 제거했다.
Python 모듈은 내부 계약 클라이언트로 남고, 케이스 스냅샷 표현은 별도 순수 모듈에 둔다.
Python의 일반 API·인증·주소·레이트 리밋 파일 16개와 미사용 CRUD 입력 스키마를 삭제했다.
챗봇 자금 실행·저장은 Spring의 공개 계산과 같은 코드 경로를 사용한다. 중복 경로 감사는
`scripts/audit_python_routes.py`, 실제 HTTP 회귀 연결은 `tests/service_client.py`가 담당한다.
Python 회귀 테스트는 실행기가 띄운 격리 Spring에 연결하며 실제 DB·Redis 확인 후 진행한다.
Spring 도메인 자체의 단위·저장·권한·롤백 검사는 Kotlin 테스트가 담당한다.
`sh scripts/run_platform_tests.sh`는 단위 검사 후 Testcontainers 전용 PostgreSQL·Redis에서 `*IT`를 실행한다.
스키마는 기존 Alembic 이미지로 적용하고 외부 분석·메일 발송만 대역으로 둔다. Python 회귀는 AI/데이터와
실제 Spring 연결·호환성 검증을 위해 유지한다. 위치·명령·대역 범위는 [실행과 검증](architecture.md#backend-실행과-검증)을 따른다.
모델 기반 AVM·자연어 해석·문서 분석과 기존 통계 보정·추천 점수·의사결정 규칙은 Python에 남아 있다.
새 계산 엔진·반올림·미검증 정책 범위는 [계산 책임](architecture.md#calculations)을 따른다.
`services/platform/`의 인증·매물·케이스·거래 준비·분석 이력·Redis 작업 계약과 Python 내부 분석 계약을 추가했다.
현재 웹 3002는 Caddy → Next.js/Spring, API 8002는 Spring이다. Python은 내부 전용이며 API·실행기 저장은 Spring 계약으로 연결한다.
일반 백엔드 이전 당시 검증은 Python 1,095개·Kotlin 25개·브라우저 56개·오프라인 평가 34건 통과였다.
2026-10-02 권리 실패 처리·비교사례 분류·동/호 입력·최소 근거를 반영한 최신 검증은 아래 기록을 따른다.
Docker 반영 후 서비스 연결과 실제 카카오 주소 조회도 확인했다. Google 실계정·Resend 실발송은 별도 검증이 필요하다.
재설정·OAuth·메일·탈퇴·주소·직접 등록·관심 지역·운영 API·AI 접수와 상태 조회는 Spring이 제공한다.
Python은 내부 AI·데이터 분석만 제공하며 Spring이 확인한 사용자 ID를 받는다. 이전 JWT·주소 증명은 테스트 자료에서 호환성을 검증한다.
null 처리 정책·실행 방법·검증 상태·내부 계약은 [백엔드 전환 안내](architecture.md#backend)를 따른다.

기존 매물 보관함·케이스·분석·체크리스트·거래 준비 모델 위에 **다섯 판단 축의 공통 평가 계약과 매수 검토 요약 화면**을 추가했다. 자금 입력의 의미도 화면·대화·시나리오에서 통일했다. 새로운 전국 Property DB나 개인화 모델을 만드는 작업은 아직 아니다.

```text
URL / 직접 입력 / CSV로 관심 매물 등록
  → 매수 케이스에 후보 저장
  → 공통 매수 조건 + 후보별 가격·자금·권리 분석
  → 매수 검토 요약: 적합성·가격성·자금성·위험성·실행성
  → 후보 비교와 사용자 선택·제외 이유
  → 다음 행동·거래 준비 작업
  → 원본 변경·만료·조건 변경 시 확인 및 재계산
```

네이버 지도 검색과 원문 추출은 보조 입력이다. 직접 등록으로 진행할 수 있으며, 추출 실패를 거래 완료나 안전으로 해석하지 않는다. 동네 탐색의 단지 추천과 실제 광고 매물은 구분한다.

직접 등록에는 주소 검색·건물명 자동 채움과 선택 별칭을 추가했다. 도로명·지번·법정동·좌표·출처·조회 시각을 저장하고 후보 및 요약·비교에 보존한다. 별칭은 분석 이름을 대체하지 않는다. 서명된 선택 정보는 사용자·만료·내용을 저장 시 검증하며 로그인 토큰이나 저장 자료에 사용하지 않는다. 상세 계약과 최신 검증은 [주소 기반 등록](features/listings.md#address-registration)을 따른다.

주소 선택 후 건축물대장 공개 정보 조회도 연결했다. 단지 전체와 선택한 건물·호실·층의 자료를 구분하고,
동·호는 각각 생략할 수 있다. 여러 건물 중 첫 경비실을 자동 선택하지 않으며, 확인된 전유면적·제공된 층은
사용자가 적용 버튼을 눌러야 반영한다. 조회 실패에도 직접 등록을 유지한다. 공식 조회 근거와 사용자 입력의
면적 차이를 기존 JSON·변경 이력·후보 스냅샷에 보존한다. 공개 API와 선택 증명 검증은 Spring이 담당한다.
다가구 호별 면적대장·주택가격·부속지번과 기존 AI 내부 건물 조회의 전면 이관은 이번 범위가 아니다.
계약과 제공 범위는 [건축물대장 조회](features/listings.md#building-register)를 따른다.

| 저장 단위 | 현재 역할 | 후속 기획과의 관계 |
|---|---|---|
| `ImportedListing` | 사용자별 광고·직접 확인값·출처·확인 시각 | 물리적 부동산 객체를 완전히 식별한 `Property`와는 다름 |
| `ListingRevision` | 사용자가 저장한 가격·상태 등 변경 이력 | 시간 관리의 기존 기반 |
| `ListingObservation` | 원문 조회의 성공·실패·추출값·관측 시각 | 조회 실패와 거래 상태를 분리. Listing Time Machine 전용 화면·지표는 후속 |
| `PurchaseCase`·`CaseProperty` | 매수 조건·후보 스냅샷·저장 분석·검토 항목·선택 기록 | Buyer Decision Graph의 기록 기반. 자동 선호 학습은 미구현 |
| `CaseExecutionPlan`·`CaseExecutionTask` | 선택 후보의 거래 준비 작업·일정·확인 결과 | 실제 협상·계약·잔금·등기를 수행하는 플랫폼의 완성을 뜻하지 않음 |

## 다음 작업자가 유지할 계약

`GET /api/cases/{id}/summary`는 본인 케이스의 `case`·`comparison`·`decision`을 반환한다. 타인 또는 없는 케이스는 404다. [case_decision_assessment.py](../services/intelligence/backend/services/case_decision_assessment.py)가 저장된 자료에서 평가를 계산하고, [case_comparison_service.py](../services/intelligence/backend/services/case_comparison_service.py)가 같은 기준을 사용한다. 조회에서 외부 API·LLM·작업 실행·선택 상태 변경을 하지 않는다.

자료 부족은 미확인이고 만료·원본 변경으로 사용할 수 없는 금액은 현재 비교에서 제외한다. 권리 문서 업로드와 실제 판독 성공은 별도다. `review_ready`는 등록 자료와 검토 항목이 확인된 상태이며 거래 안전 인증이 아니다. 미확인 상태에서 사용자가 후보를 선택하면 보완 필요 표시를 유지한다. 전체 점수나 자동 매수 결론을 추가하지 않는다.

자금의 `owned_homes`는 취득 후 주택 수이며 첫 주택은 1이다. `home_count_basis="after_purchase"`를 유지한다. 공통 프로필의 비상자금은 한 번만 제외하고, 이미 반영한 후보별 가용 현금에서 다시 빼지 않는다. 저장된 개별 조건은 공통 조건과 다를 수 있다. 공통 조건 적용은 사용자 선택으로 제공하고 현재 후보 가격과 계산 가격의 일치는 확인한다.

프론트엔드의 `/cases/{id}/summary`와 비교 화면은 서버의 공통 결과를 표시한다. [DecisionAxisCard.tsx](../web/src/components/DecisionAxisCard.tsx)가 근거·누락·연결 행동을, [candidateSimulationSeed.ts](../web/src/lib/candidateSimulationSeed.ts)가 후보와 저장 자금 조건의 전달을 담당한다. 세션 상태는 기존 `sessionStore.ts`의 구독 경로를 사용한다.

## 1단계의 남은 우선 작업

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 실제 아파트 전체 흐름 평가 | 등록 → 실제 AVM → 자금 → 권리 → 비교 → 선택 → 다음 행동 → 새로고침 → 원본 변경 후 재검토를 재현. 근거 부족·낮은 신뢰도·잘못된 PDF·수집 실패·금액 변경도 검증 |
| 2 | 공식 부동산 객체 연결 | 주소·이름·별칭·출처·동/호/층·면적 기준과 건축물대장 건물·호실 근거를 연결했다. 단일 Property 마스터·유형별 기준정보와 이관 계획은 후속. 같은 주소의 광고를 자동 병합하거나 공부상 호실 확인을 현재 광고·소유권의 확인으로 표시하지 않음 |
| 3 | 근거 품질 평가 | 실거래 원금액·거래일·관측일·면적 차이·선정 이유, 권리 문서 페이지·명시 발급일·최소 발췌는 반영했다. 실제 발급 PDF의 레이아웃·말소·누락·OCR 정확도와 AVM 재백테스트는 후속. 원문 PDF 영구 보관은 도입하지 않음 |

실제 사례에서 계산 입력과 독립 수기 정답, AVM 비교 거래, 사람이 확인한 문서 위험 항목을 별도로 대조한다. 브라우저 화면이 연결되는지와 분석 자체가 정확한지는 다른 평가다. 이 기준을 충족하기 전에는 1단계 전체 완료로 설명하지 않는다.

그 이후에 시간 변화 요약·명시적 선호·임장·협상 기록, 주거 유형 확대를 진행한다. 상업·산업·토지는 각 유형의 자료·분석·검증이 확보된 순서로 추가한다. 공급자 등록·소유자 인증·Marketplace·매수/매도자 연결과 모바일 앱은 후속 계획이다.

### 유형별 AVM 기준 정립과 다음 구현

2026-10-04 [PC-AVM-1.0](features/decision.md#valuation-standards)을 기존 의사결정 문서에 통합했다.
아파트·오피스텔·연립/다세대·단독·다가구·구분상가·구분사무실·전체 빌딩·공장·창고/물류시설·토지의
평가 단위, 방법별 필수 입력, 가치 요인, 비교/수익/원가/공시자료/개발/ML 경로와 보류 조건을 정했다.
법정 감정평가 원칙과 서비스의 참고 분석 정책을 구분하고, 시장가격 참고·조건부 시나리오·구성 부분·보류·미지원의

## 실행과 공개 운영 준비

기본 호스트 포트는 웹 **3002**, Spring API **8002**이고 컨테이너 내부는 Next 3000·Spring 8080·Python 8000이다. Python·Docker는 WSL, Node·npm은 Windows에서 실행한다. PostgreSQL·Redis·별도 작업 실행기가 필수다. pytest는 `scripts/run_isolated_tests.py`로 전용 DB·Redis를 사용하며 서비스 데이터에 연결하지 않는다.

공개 서버·도메인은 아직 준비되지 않았다. HTTPS·프록시·백업·외부 감시 설정을 작성한 상태와 공개 운영 적용은 구분한다. Resend 도메인 인증, 실제 OAuth 리다이렉트 등록, 외부 접속·장애 감지·복원은 배포 환경에서 별도 확인한다. 운영자는 [운영 안내](operations.md#administration), [작업 복구](operations.md#job-recovery), [로컬 WSL 운영](operations.md#local-runtime)을 따른다.

`.env`는 비공개 설정이며 설명은 `.env.example`을 기준으로 관리한다. `sh scripts/compose.sh dev config`는 실제 키를 출력할 수 있으므로 로그나 문서에 붙이지 않는다. 생성 LLM과 임베딩 제공자 설정은 별도로 확인하고 기존 벡터와의 호환을 유지한다.
