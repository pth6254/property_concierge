## 다섯 판단 축과 검토 기준

매수 케이스의 **매수 검토 요약**에서 후보별 적합성·가격성·자금성·위험성·실행성을 확인한다. 각 축은 사용한 값·출처·기준 시각과 부족한 정보를 보여주고, 해당 입력·분석·검토 화면으로 연결한다. 후보 선택은 사용자가 한다.

<a id="decision-assessment-이용-흐름"></a>

### 이용 흐름

1. 매물 보관함에 관심 매물의 URL 또는 직접 확인한 값을 등록하고 매수 케이스에 후보로 저장한다.
2. 케이스에서 예산과 공통 매수 조건을 입력하고 후보별 시세·자금·권리 분석을 실행한다.
3. **매수 검토 요약**에서 후보별 확인 상태와 판단 근거를 비교한다.
4. 다음 행동으로 부족한 입력·서류·현장 확인을 보완한다. 후보 비교에서 선택 이유를 저장하면 거래 준비 작업으로 이어진다.

포털의 매물 추출 성공은 필수 조건이 아니다. 직접 입력한 후보도 검토할 수 있으나 출처·확인 시각을 연결하지 않으면 미확인 사항으로 남는다.

<a id="decision-assessment-판단-축과-표시-기준"></a>

### 판단 축과 표시 기준

| 축 | 사용하는 자료 | 현재 표시 기준 |
|---|---|---|
| 적합성 | 예산, 면적, 물건 유형, 관심 지역의 법정동 코드 | 설정된 조건만 비교한다. 후보의 준공연도가 없으면 연식 조건은 미확인이다. 지역 이름만으로 법정동을 추정하지 않는다. |
| 가격성 | 희망가, 저장된 AVM 추정가·신뢰도·비교사례 수 | 유효한 기준일, 양수 가격, 신뢰도 50% 이상 및 100% 이하, 비교사례가 있을 때 가격 차이를 계산한다. 희망가가 추정가보다 5% 넘게 높으면 재검토를 안내한다. 이 값은 서비스의 확인 기준이며 적정 매수가격이나 정확도 보장이 아니다. |
| 자금성 | 후보 가격과 저장된 계산 결과·입력 조건 | 현재 가격으로 계산했는지, 취득 후 주택 수가 기록됐는지, 현금·첫 달 상환액·소득 등 필요한 기준이 있는지 확인한다. 현금 부족·상환 부담·계산기에 적용된 대출 기준 초과는 주의로 표시한다. |
| 위험성 | 업로드 문서의 판독 결과와 위험 신호, 매물 출처 확인 | 등기부·건축물대장 판독 여부를 업로드 여부와 구분한다. 둘 다 판독되지 않았거나 원본 확인 시각이 없으면 검토 완료로 표시하지 않는다. 과거 위험 신호는 만료 후에도 재확인 대상으로 남긴다. |
| 실행성 | 위 네 축, 체크리스트와 다음 행동, 사용자 선택 기록 | 네 축의 근거와 등록된 확인 항목이 모두 해결된 경우에만 등록 검토 항목 확인으로 표시한다. 체크리스트 완료율을 추천 점수로 사용하지 않는다. |

상태는 `등록 자료 확인`, `주의·재검토`, `미확인`, `갱신 필요`, `분석 실패`, `분석 중`을 구분한다. ‘등록 자료 확인’은 저장된 자료로 해당 기준을 비교할 수 있다는 뜻이며 거래 안전성의 인증이 아니다.

매물 원본 변경·재확인 필요, 분석 만료·기준일 누락·미래 시각, 후보 가격과 자금 분석 가격의 불일치가 있으면 이전 결과를 현재 비교 금액에 사용하지 않는다. 과거 값은 근거에서 이전·미확인 값으로 구분해 볼 수 있다. 기준 시각을 모르는 자료에 조회 시각을 임의로 채우지 않는다.

<a id="decision-assessment-구현-계약"></a>

### 구현 계약

`GET /api/cases/{id}/summary`는 소유자 확인 후 `case`, `comparison`, `decision`을 반환한다. `decision`은 버전·조회 시각·후보별 다섯 축·현재 사용 가능한 비교 금액·다음 행동·결과의 한계를 포함한다. 각 근거의 출처는 사용자 입력·공식 실거래 자료·계산 결과·문서 분석·작업 기록으로 구분한다.

`services/intelligence/backend/services/case_decision_assessment.py`가 같은 케이스 자료에서 결과를 계산한다. 후보 비교도 이 결과의 검토 완료 여부와 가격 차이를 사용한다. 조회 중 외부 API·LLM·새 작업을 실행하거나 선택 상태를 변경하지 않는다. 별도 테이블이나 데이터 이관 없이 기존 후보·분석·체크리스트를 사용한다.

자금 분석은 후보에 저장된 개별 입력을 사용하며 공통 조건과 다르다는 이유만으로 무효화하지 않는다. 재계산 화면에서는 저장된 입력과 공통 조건 적용을 선택할 수 있다. 권리 원문 PDF는 저장하지 않으며 판독 상태와 최소 근거만 요약에 추가한다. 이전 권리 결과에 판독 기록이 없으면 다시 분석해야 한다.

<a id="decision-assessment-검증-범위"></a>

### 검증 범위

- `tests/test_case_decision_assessment.py`: 다섯 축의 근거, 상태 구분, 기준일 누락·미래 시각·만료, 원본 변경, 가격 차이, 자금 입력 부족, 판독 실패, 법정동 범위와 자동 선택 방지를 확인한다.
- `tests/test_purchase_cases.py`: 실제 API의 소유자 격리, 조회 후 상태 보존, 판독할 수 없는 PDF의 확인 상태를 검증한다.
- `services/intelligence/evaluation/datasets/decision.json`: 고정 시각의 가상 케이스를 재생한다. 비교사례 수·문서 판독·취득 후 주택 수·매물 확인 시각은 선언된 검증용 입력이며 실제 매물 또는 문서 판독 실적이 아니다.
- `scripts/verify_decision_assessment_browser.cjs`: 실제 자금 계산·후보 저장, 다섯 축 표시·근거 확인, 조건 전달, 가격 수정 후 재검토, 새로고침 복원, 미확인 상태에서 사용자 선택, 좁은 웹 화면을 확인하고 임시 계정을 삭제한다.

브라우저 결과는 `evaluation-results/assessment-browser*.json`과 화면 이미지에 저장한다. CI에도 이 흐름과 아티팩트 보관을 추가했다. 실행 중인 서비스에는 `node scripts/verify_decision_assessment_browser.cjs`, 개발 프론트엔드를 따로 띄울 때는 명령 뒤에 API 주소를 전달한다.

2026년 10월 1일 격리 DB·Redis에서 백엔드 전체 테스트 1,065건이 통과했고 1건은 건너뛰었다. 프론트엔드 타입·린트·프로덕션 빌드와 Docker 재빌드가 통과했다. 실제 Docker 서비스와 로컬 개발 프론트엔드에서 통합 의사결정 브라우저 검증 13개 항목이 각각 통과했으며 임시 계정 삭제 응답은 모두 200이었다. 기존 자금 브라우저 검증 13개 항목과 화면 이동 검증 7개 항목도 통과했다. 로컬 개발 프론트엔드 검증은 로컬 API에 연결했으며 원격 GitHub Actions 실행 완료를 의미하지 않는다.

이 검증은 저장된 근거를 올바르게 연결하고 불확실성을 표시하는지 확인한다. 실제 AVM 정확도, 문서 위험 신호 탐지 정확도, 실호가·매물 존재, 최신 세금·금융 규칙의 전체 예외, 사용자 투자 성과를 보장하지 않는다. 통근·학군·소음·주차 자료, 실제 발급 문서의 판독 품질과 부동산 객체의 완전한 동일성은 후속 작업이다. 모바일 앱 개발은 이후 단계로 둔다.

## 유형별 AVM 가치평가 기준 v1.0

기준 ID **`PC-AVM-1.0`**, 정립일 **2026-10-04**. 이 절은 입력·분석·평가·화면 구현이 함께 따를
**서비스 설계 기준의 단일 원본**이다. 상업·업무용의 입력 임대료 시나리오와 토지 공개정보는
아래 [적용된 기능](#valuation-support)에 연결했다. 2026-10-05 공통 결과 계약과 실행 제한을 추가했지만,
모든 유형의 가격 모델·정확도 검증까지 완료한 것은 아니다.
현재 코드와의 차이는 [적용 순서](#valuation-implementation)에 기록한다.
아파트 매수 의사결정 기반을 먼저 완성하고, 나머지 유형은 데이터와 유형별 검증이 확보된 순서로 적용한다.

### 적용 목적과 법령 참고 범위

서비스 목적은 **매수 검토를 위한 시장가격 참고와 입력 조건별 수익성 분석**이다. 법정 감정평가서,
담보 인정금액, 보상금, 과세가액을 산출·보증하는 기능으로 설명하지 않는다. 기존 입력에 담보·경매·과세·보상이
있다는 사실도 해당 목적의 평가 기능 구현을 뜻하지 않는다. 그 목적은 별도 전문 검토 대상으로 안내한다.

2026-10-04 국가법령정보센터에서 확인한 [「감정평가에 관한 규칙」](https://www.law.go.kr/법령/감정평가에관한규칙)은
2023-09-14 시행본이다. 참고하는 조항은 다음과 같다. 실제 법정 감정평가에 적용되는 원칙과 이 서비스의
출력 허용 정책은 별개이며, 아래 표본 수·검증 조건을 법령의 요구로 설명하지 않는다.

| 참고 조항 | 설계에 반영할 원칙 |
|---|---|
| 제5~7조 | 기준가치·기준시점의 현황·평가 단위를 먼저 확인. 여러 물건을 일괄하거나 일부만 평가할 때 범위를 명시 |
| 제11~12조 | 비교·원가·수익 방식 구분. 대상에 맞는 방법과 다른 방법의 합리성 검토, 적용이 곤란한 사유 기록 |
| 제14조 | 토지의 공시지가기준법은 비교표준지 선정과 시점·지역·개별 요인 등의 검토를 포함. 개별공시지가에 배수를 곱한 값과 구분 |
| 제15~16조 | 건물의 원가법과 토지·건물 일괄평가의 거래사례비교법 구분. 구분소유 건물부분과 대지사용권의 일괄평가 포함 |

### 평가 대상을 먼저 확정한다

자산 유형, 평가 단위, 실제 이용, 가격 기준을 별도 항목으로 관리한다. **주거/상업/업무/산업/토지라는
5개 라우팅 분류만으로 평가 방법을 확정하지 않는다.** 아래 명칭은 설계용 분류이며 현재 저장 enum을 바꾼 것은 아니다.

| 확인 축 | 값과 처리 기준 |
|---|---|
| 자산 세부 유형 | 아파트·오피스텔·연립/다세대·단독·다가구·구분상가·구분사무실·건물 전체·공장·창고/물류시설·토지. 복합용도는 용도별 면적과 수입을 분리 |
| 평가 단위 | 개별 호실, 토지와 건물 전체, 건물만, 토지만, 복수 필지/동. 단지·구 평균을 개별 호실 전체가격으로 표시하지 않음 |
| 실제 이용 | 자가사용, 임대운영, 공실, 개발 검토. 건축물대장 용도·사용자 진술·확인된 현황이 충돌하면 확인 필요 |
| 거래·권리 범위 | 매매가격과 보증금/임대료 구분. 토지 지분·대지권·임차인 보증금 승계·별도 설비/영업권 포함 여부 명시. 지분거래는 전체가격의 단순 비례 추정 대상에서 제외 |
| 기준시점·가치 | 분석 기준일, 시장가격 참고/조건부 투자 시나리오 구분. 미래 준공·허가·임대계약 체결을 현재 확정 사실로 취급하지 않음 |

동·호는 계속 선택 입력이다. 생략 시 주소·단지·면적형 수준의 참고 분석은 가능하지만 실제 동·호 확인으로
표시하지 않는다. 입력 동·호와 공부가 충돌하면 개별 호실 분석을 보류한다. 건물 전체나 토지는 동·호를 요구하지 않는다.
모르는 유형을 아파트로 자동 대체하거나, `detached`라는 기존 값만으로 단독과 다가구를 확정하지 않는다.

### 공통 자료와 출처 기준

모든 분석은 물건 식별 근거, 대상 범위, 기준일, 면적의 의미, 자료 출처와 확인 시각을 보존한다.
**등록 허용 조건과 가격 산출 조건은 별개**다. 자료가 부족해도 매물 저장은 가능하고 분석만 보류할 수 있다.

| 자료 | 필수 의미·단위 | 사용 범위와 미확인 처리 |
|---|---|---|

### 유형별 필수 입력과 평가 방식

여기서 ‘필수’는 **해당 방법으로 가격을 산출할 때 필요한 자료**다. 비교·수익·원가 중 한 방법의 자료가
부족하면 그 방법만 실행하지 않는다. 모든 유형에 수익 자료나 동·호를 필수로 요구하지 않는다.
‘우선 경로’는 매수 검토 서비스의 분석 순서이며 법정 감정평가의 주된 방법을 대체하는 선언이 아니다.

승인 여부·시기·대상 필지의 수혜를 확정하거나 가격을 일률적으로 가산하지 않는다.

### 방법별 실행·보류 기준

아래 수치는 **PC-AVM-1.0의 초기 연구/출력 정책**이다. 검증으로 변경할 때 기준 버전과 변경 전후 평가를 남긴다.
최종 평가 결과를 본 뒤 통과하도록 기준을 바꾸지 않는다.

| 방법 | 실행에 필요한 근거 | 허용 결과·자료 부족 시 처리 |
|---|---|---|
| 실거래 비교 | 동일 평가 단위·유형·면적 기준, 양수 가격, 해제/중복/특수거래 점검, 기준일 이전 거래 | 아파트의 우선 연구군은 최근 6개월·동일 단지·전용면적 ±10% 내 유효 거래 5건 이상. 3~4건은 사례 참고, 0~2건은 개별 가격 산출 보류. 12개월까지 확장한 과거 자료는 별도 표시하고 검증된 시점수정 필요 |
| 비아파트 거래 비교 | 유형별 위 표의 필수 특성과 사례 범위, 거래 범위 대조 | 아파트의 면적·표본 기준을 복제하지 않음. 유형별 대표 표본과 출시 기준을 확보하기 전에는 사례 비교만 제공하고 검증 완료된 가격 모델로 표시하지 않음 |
| 직접 수익환원 | 같은 기간/범위의 임대수입·공실/미수·소유자 운영비, 독립된 시장 환원율 근거 | 정상화된 NOI ÷ 환원율. 가정에 의존하면 조건부 시나리오. 환원율 ≤0 또는 NOI ≤0이면 이 방법의 양수 자본가치 추정 보류; 물건 가치 0으로 해석하지 않음 |
| DCF | 기간별 임대·공실·운영비·수선/투자비, 할인율, 보유기간·말기가치·처분비 근거 | 현금흐름·가정을 노출한 조건부 분석. 계약/기간별 자료가 없으면 직접 수익환원값을 DCF라고 표시하지 않음 |
| 토지·건물 구성/원가 | 토지 가격의 기준·원/㎡, 재조달비의 시점·용도·구조·면적 기준, 물리/기능/경제적 감가 근거 | 건물 가치와 토지가치를 별도 표시. 건물만 산출됐으면 부분 가치. 원가 추정과 거래 가능한 전체 시장가격을 구분 |
| 공시자료 기반 토지 검토 | 표준지/개별공시지가 구분, 기준일·필지, 비교·보정 근거 | 비교표준지·보정 검토가 없으면 ‘공시자료 참고’로 한정. 개별공시지가를 확정 시세·법정 공시지가기준법 결과로 표시하지 않음 |
| 개발 잔여가치 | 확인된 규제/허가 범위, 개발 일정, 준공 후 수입/가치·공사비·부대비·금융비·사업 이익 가정 | 토지의 현재 시세와 분리된 개발 시나리오. 비용·허가·완공가치 핵심 조건 미확인 시 가격 산출 보류 |
| ML 추정 | 적용 유형/단위/지역/가격대가 학습·검증 범위 안에 있고 필요한 특성과 배포 검증 기록 존재 | 기존 방법을 기준선으로 비교. 학습 밖 자료·검증 미완료·입력 충돌 시 보류. 아파트 CatBoost를 타 유형에 그대로 적용하지 않음 |

구·동 평균밖에 없으면 ‘지역 통계’를 제공한다. 반경·기간만 넓혀 다른 시장의 거래 수를 채우지 않는다.
향·조망·소음·상권·도로 등 미확인 요인은 미확인으로 남기며 ‘누락값=중립/안전’으로 해석하지 않는다.
핵심 면적·거래 단위 불명은 산출 보류, 부가 특성 누락은 적용 범위 제한과 보정 미실행으로 구분한다.

수익 분석에서는 **부동산 자체의 NOI와 매수자의 자금 현금흐름을 분리**한다. 대출 원리금·취득세·매수자 소득세를
NOI 운영비에 섞지 않는다. 대수선 등 자본지출은 가정과 포함 위치를 명시하고 DCF에서 이중 차감하지 않는다.
보증금은 연 임대수입으로 단순 합산하지 않으며, 승계 보증금으로 줄어드는 매수 현금과 부동산 총가치를 구분한다.
임대료·공실률·환원율의 낙관/기준/비관 조합은 독립 가정의 시나리오이며 통계적 예측구간이라고 표시하지 않는다.

### 방법 선택과 결과 표시 계약

예정 흐름은 **대상 범위 확인 → 자료 점검 → 가능한 방법별 산출 → 근거·불일치 검토 → 결과 종류 결정**이다.
서로 다른 방법의 값을 무조건 평균하지 않는다. 검증된 결합 모델이 없다면 각 방법의 값과 차이 원인을 나란히 표시한다.
수익환원과 DCF가 같은 임대자료를 사용하면 완전히 독립된 두 근거로 세지 않는다.
신뢰 가능한 방법끼리 20%를 넘게 벌어지면 단일 통합가 산출을 보류하는 초기 정책을 둔다.
차이는 `(큰 값 - 작은 값) / 작은 값`으로 비교하며 양수·동일 범위·동일 기준일의 결과에만 적용한다.

| 결과 종류(설계용) | 화면에 보여줄 내용 | 매수 비교에 사용할 범위 |
|---|---|---|
| 시장가격 참고 | 방법·가격·기준일·사용 사례·적용 범위·누락 요인 | 유효한 같은 범위/기준의 결과만 가격 차이 계산에 사용. 법정 감정평가·매수 승인이 아님 |
| 조건부 시나리오 | 사용자/분석 가정과 시나리오별 값 | 시나리오끼리 비교. ‘실거래 대비 저평가’ 근거로 사용하지 않음 |
| 구성 부분 참고 | 건물만/토지만 등 산출된 범위와 누락 구성 | 토지+건물 전체 호가와 직접 할인율 계산 금지 |
| 자료 부족·추정 보류 | 보류 이유·부족한 입력·다음 행동, 가격 `null` | 현재 비교 가격에서 제외. 0원·이전 결과·LLM 임의 가격으로 대체하지 않음 |
| 지원 범위 밖 | 유형·목적·권리 형태 중 미지원인 내용 | 가능한 자료 조회/메모는 유지하고 가격 판단은 제공하지 않음 |

결과에는 기준 버전, 평가 목적·단위·유형·기준일, 사용/미사용 방법과 이유, 금액 단위,
근거별 출처·자료 기준일·관측일, 가정, 누락 정보, 모델 버전·검증 범위, 결과 종류와 다음 행동을 보존한다.
입력의 객체·면적·토지 범위·임대 조건·기준일이 바뀌면 이전 결과를 보존하고 해당 분석을 재검토한다.
기존 `expected_inputs`·후보 스냅샷·분석 이력·다섯 판단 축의 최신성 판단과 연결한다.
이 결과 종류는 기존 `decision` 상태 enum의 교체가 아니며 향후 가격 분석의 추가 메타데이터로 설계한다.

기존 `confidence`는 자료·매칭 기반 참고 점수다. **80%라는 점수만으로 80% 적중 확률을 주장하지 않는다.**
유형·지역·기간·표본·방법이 일치하는 별도 보정 검증이 있어야 확률 해석을 검토할 수 있다.
고정 ±10%/±15% 범위는 검증된 예측구간이 아니다. 예측구간을 제공하려면 명목 포함률과 이후 거래의 실제 포함률,
구간 폭을 함께 검증한다. 데이터 품질·모델 오차·권리 위험을 하나의 신뢰 점수로 합치지 않는다.

### ML·LLM과 서비스 책임

| 책임 | 구현 원칙 |
|---|---|
| Kotlin / platform | 입력 검증·소유자 확인·저장·변경 재검토·작업 상태, 확정 입력의 NOI/수익환원/DCF/자금 등 고정 수식. 기존 Python 원가/수익 계산은 계약·고정 회귀값과 함께 단계적으로 이전하며 이중 실행 원본을 만들지 않음 |
| Python / intelligence | 자료 분석·비교사례 선정·유형별 모델·임대료/공실/보정 추정·적용 범위 판단·가격 근거 구성. 실제 가격 산출과 독립된 검증 자료 유지 |
| LLM | 원문에서 근거를 연결한 조건 추출·설명·확인할 항목 제시. 임대료·환원율·개발 승인·누락된 가격을 사실처럼 생성하지 않음. 수치 가드레일 유지 |

자료가 적은 유형은 직접 가격 예측부터 강제하지 않는다. 충분한 관측값이 있는 임대료·공실 등 요소 추정과
기존 기준선의 오차 보정부터 검토한다. 다른 지역 자료를 통합 학습하더라도 대상 지역에서 별도 검증한다.
아파트 CatBoost의 첫 비교 기준 미달과 오프라인 후보 상태는 [기존 모델 평가](#price-model-comparison)를 유지한다.

### 평가와 적용 승인 기준

아래는 **향후 구현의 완료 기준**이다. 아직 수행하지 않은 비아파트 검증을 완료로 기록하지 않는다.
독립 평가·대표 표본·지속 점검의 원칙은 [IAAO AVM 기준 2018, §7](https://www.iaao.org/wp-content/uploads/Standard_on_Automated_Valuation_Models.pdf)을 참고한다.
유형별 수익·원가·거래 자료의 선택은 [IAAO Mass Appraisal 2023, §4](https://www.iaao.org/wp-content/uploads/2023_Oct_20_StandardOnMassAppraisal_Updated-clean.pdf)를 참고하되 국내 법정 기준을 대체하지 않는다.

| 검증 층 | 정답과 분리 기준 | 통과 여부 판단 |
|---|---|---|
| 객체·정책 | 유형/단위/면적/권리 범위가 명시된 검토 사례와 아래 수용 사례 | 미확인을 확인됨으로 표시, 다른 평가 단위 혼합, 보류값을 0원으로 대체하는 오류 0건 |
| 고정 수식 | 입력과 기준일을 고정한 독립 수기 정답. Kotlin 단위·통합 검사 | 원/만원, 월/연, 소수율/퍼센트, 보증금·비용의 중복 반영, 반올림을 확인. 모델 결과를 수식 정답으로 삼지 않음 |
| 시장가격 모델 | 해제/정정 확인된 동일 범위 실거래. 시간순 학습→검증→최종 평가, 필요시 건물/단지·지역 홀드아웃 추가 | MAPE·중앙 APE·P90 APE·MAE·±10/20% 적중률·방향 편향·추정률. 실패·보류도 전체 요청 분모에 유지 |
| 임대·수익 요소 | 기간/포함 비용이 확인된 실제 임대계약·운영 내역. 매매 호가와 구분 | 임대료 오차, 공실률 %p 오차, NOI 수기 대조, 환원율의 출처·기간·동일 자산 대조. 시장가 검증 없이는 수익 시나리오 계산 검증까지만 표시 |
| 원가·토지 구성 | 출처·시점·구조가 확인된 원가/토지 자료와 독립 검토 | 계산 재현과 전체 시장가 적중을 별도 보고. 공시가격을 매매가격의 정답으로 사용하지 않음 |
| 설명·화면 | 실제 산출 근거·보류 이유·사용자 입력·복원 상태 | LLM의 근거 밖 숫자/가격 생성 0건, 결과 종류·단위·시점 표시, 케이스 비교에서 부분/조건부 결과 오용 0건 |

거래의 최초 관측/공표 시점이 없으면 거래일 기준 회고 평가라고 명시한다. 평가 대상을 자기 비교사례로 쓰거나,
미래 거래·해제 사실·현재 공시값을 과거 학습 입력에 넣지 않는다. 데이터 분할마다 집계/단가/보정 특성을 과거 자료로 다시 만든다.
호가·공시가격·다른 AVM·LLM 출력은 실거래 정답을 대신하지 않는다. 동일 거래의 재수집 중복은 같은 분할에 놓거나 제거하되,
같은 날 같은 가격의 서로 다른 거래까지 단순 중복으로 삭제하지 않는다.

아파트 CatBoost의 기존 후보 기준(짝지은 100건, 지역별 20건, MAPE 상대 개선 5%, 적중률/추정률 비악화,
지역 MAPE 악화 2%p 이내)은 **단일 실험의 최소 비교 조건**으로 유지한다. 서비스 적용 전에는 다음 항목도 필요하다.

1. 같은 대상 표본의 기준선 대조와 모든 요청의 추정률을 함께 보고한다. 모델이 어려운 표본을 보류해 평균 오차만 좋아진 경우를 구분한다.
2. 최종 평가 전에 허용 오차·최소 추정률·최소 표본·예측구간 조건을 유형/지역/가격대별로 기록한다.
   비아파트의 수치 기준은 아직 검증 자료가 없으므로 **미승인**이며 아파트 기준으로 자동 승인하지 않는다.
3. 최소 3개의 겹치지 않는 이후 평가 구간에서 시간 이동 평가를 수행한다. 표본 부족 구간은 통과로 처리하지 않고,
   구간·지역별 표본과 성능 변동/불확실성을 보고한다. 충분한 검증 표본을 정하는 것이 어려우면 배포 범위를 축소한다.
4. 모델/데이터/기준 버전, 특성 목록·단위, 전처리·분할 설정, 데이터/모델 해시, 사용 환경과 평가 결과를 보관한다.
   검증 창을 보고 튜닝하면 그 창은 개발 자료가 되며 이후의 새 최종 평가가 필요하다.
5. 유형별 공개 적용은 명시적으로 결정한다. 배포 후 자료 분포·보류율·관측된 오차를 점검하고,
   검증된 범위를 벗어나면 모델을 중단하거나 이미 검증된 기준선으로만 복귀한다. 근거가 없는 기준선 대체도 금지한다.

### 현재 코드와 적용 순서

**보류 시 참고 거래 (2026-10-08):** 아파트가 비교사례 5건 미만으로 보류되면 `valuation.reference_context`에
동일 단지·최근 12개월·전용면적 ±20%의 신고 거래(최대 10건)와 ㎡당 최소/중앙/최대를 담아 화면에 표시한다.
시점수정을 하지 않았고(`time_adjusted=false`) 가격 추정·비교·가격 체크리스트에 사용하지 않는다. 결과 종류는 `withheld`로 유지한다.
동일 단지가 아니거나 해제·기간 밖·면적 밖 거래는 담지 않으며, 근거 자료가 없으면 이 항목은 비어 있다.

**전세가율 참고 (2026-10-08):** 아파트 분석에서 국토부 전월세 신고(`RTMSDataSvcAptRent`)를 12시간 Redis 캐시로 조회해
`valuation.jeonse_context`에 동일 단지·전용면적 ±10%·최근 6개월 전세(월세 0)의 ㎡당 중앙값과 같은 조건 매매 ㎡당 중앙값의 비율을 담는다.

시점이 다른 신고를 섞은 참고 비율이며 가격 추정·비교·위험성 축 상태에는 아직 연결하지 않았다. 조회 실패는 가격 분석을 막지 않고 항목만 생략한다.

### 2026-10-04 적용: 임대료 시나리오와 토지 공개정보

`/appraisal`에서 **상가·사무실/오피스**를 선택하면 현재 받는 월세, 소유자 부담 운영비 최소/최대,
환원율 가정 최소/최대, 선택 매매 호가를 입력한다. 평가 범위는 개별 호실/건물 전체이며 분석일과 임대료 확인일을 맞춘다.
월세는 부가세·관리비·보증금 원금을 제외한 현재 수령액이다. 이미 공실 영향이 반영된 수령액에서 공실률을 다시 차감하지 않는다.

- 고정 수식의 실행 원본은 Spring `IncomeValuationCalculator`다. 연 월세 = 월세×12,
  NOI 하한 = 연 월세−최대 월 운영비×12, NOI 상한 = 연 월세−최소 월 운영비×12다.
- 조건부 가격 하한 = NOI 하한÷높은 환원율, 상한 = NOI 상한÷낮은 환원율이다.
  호가를 입력하면 총임대수익률과 NOI 범위에 따른 순임대수익률도 표시한다.
- 환원율은 **사용자 가정**이며 자동 수집한 시장 환원율이 아니다. 운영비가 없으면 NOI·가격은 보류하며,
  NOI 하한이 0 이하이면 양수 가격을 만들지 않는다. 음수 NOI를 자산 가치 0원으로 해석하지 않는다.
- `conditional_scenario`·`withheld` 결과에 입력·기준일·계산 버전을 보존한다. LLM 계산이나 기존 지역별 고정 임대료로 대체하지 않는다.
  미래 계약 변경·대수선·금융비용·보증금 운용수익·DCF는 이번 범위에 포함하지 않는다.

**토지**는 정확한 주소를 필지(PNU)로 변환한 후 Spring `LandInformationService`가 VWorld 토지임야정보,
토지특성정보, 개별공시지가정보, 토지이용계획정보를 병렬 조회한다. 주소가 여러 필지로 해석되면 임의 선택하지 않는다.
지목·대장 면적·이용상황·지형고저·형상·도로접면·용도지역·공시지가와 이용계획 항목을 표시한다.
공급자 응답의 PNU·건수·기준연도를 대조하며 중복·누락·만료 키·다른 필지는 미확인으로 표시한다.
현재 토지대장 면적과 특성 기준연도의 면적은 별도다. **같은 연도의 특성 면적×공시지가**만 공시 참고 총액으로 계산한다.
공시 참고 총액은 시장가격·개발 가능성·법정 감정평가액이 아니다. 과거 기준일 당시의 공개 상태를 재현하는 기능도 아니다.

공개 조회는 `POST /api/address/land`, 서비스 인증 조회는 `POST /internal/v1/land/lookup`,
계산은 `POST /internal/v1/calculations/income_valuation`이다. 내부 계약은 `contracts/v1/`에 보존한다.
주소 등록 화면에서도 토지 공개정보를 미리 보며, 분석 결과의 보관은 기존 AVM 작업·분석 이력을 사용한다.
조건부 가격·공시자료·보류 결과의 `estimated_price`는 null이고 후보 비교 금액에서 제외한다.
후보의 가격 검토 체크리스트를 자동 완료하지 않으며 출처·입력·기준일을 결과 화면에서 복원한다.
추천의 `analyze_price` 직접 호출도 임대료 입력이 없으면 보류하고, 토지는 정확한 주소가 있을 때만 공개정보로 연결한다.
구 평균 거래가격으로 이 조건을 우회하지 않는다.

공장·창고의 원가·설비 평가 확대는 보류했다. 기존 산업용 경로가 새 기준을 충족한다고 설명하지 않는다.

검증: Kotlin 단위 48개·전용 저장소 통합 20개, 관련 Python 회귀 130개, 입력→작업→이력→후보 비교→복원과
토지 오류 처리의 격리 브라우저 5개 항목을 확인했다. 외부 토지 공급자는 대역이며 실제 Kotlin 수식과 저장을 사용한다.
별도로 로컬 Docker에 반영해 서울 중구 세종대로 110의 실제 카카오/VWorld 결과, 작업 저장·복원·390px 표시를 확인했다.
새 키로 네 공개 자료가 정상 조회됐으며 실제 공급자 검증은 공개 주소 1건이다. 시장 시세 정확도 평가와 구분한다.
세부 실행·산출물은 [인수인계](../project-handoff.md#검증-상태와-경계)를 따른다.
기존 가격·자금·권리와 다섯 판단 축의 상태 의미를 유지하며, 원문 PDF·주소 확인 토큰을 영구 저장하지 않는다.

## 가격 모델의 비교와 적용 경계

서비스 가격성 판단은 기존 실거래 비교 AVM을 사용한다. CatBoost는 Python AI/데이터 영역의
오프라인 후보 모델이며 사용자 후보·비교 화면에 자동 적용하지 않는다. 학습·검증·최종 평가를 시간순으로
나누고 같은 거래에 기존 주거용 AVM을 재생하여 MAPE·±10% 적중률·추정률·지역별 악화를 확인한다.
2026-10-03 서초·강남·노원 300건 비교는 기존 AVM MAPE 12.70%, CatBoost 19.82%로 후보 기준 미달이었다.
이는 해당 기간과 표본의 회고 평가이며 전국·현재 개별 매물의 정확도 보장이 아니다.
입력 특성·출처·통과 조건·학습 모델과 보고서·다음 실험은 [가격 모델 평가](../../services/intelligence/evaluation/README.md#catboost-후보-모델과-실거래-비교-avm)를 따른다.
향후 가격 모델을 연결해도 기존 기준선·비교사례·기준 시점·미확인 상태와 사용자 선택은 유지한다.
LLM이 모델 실패를 임의의 가격으로 대신하거나 실험 성능을 매수 승인으로 해석하지 않는다.

## 실거래·권리 문서의 최소 근거

### 비교사례 매칭과 가격 근거

비교사례 표시·지역 보정과 신뢰도 계산은 `comparable_matching.py`의 같은 분류를 사용한다.
단지 조회가 실제로 성공한 이름만 동일 단지로 표시하며, 구 전체 대체 사례의 첫 단지명을 대상 단지로 간주하지 않는다.
대상의 법정동과 조회 시군구가 모두 일치해야 동일 동이다. 다른 동의 같은 이름, 복수 단지의 모호한 부분 일치와 지역 미확인을 구분한다.
이 변경은 기존 서초구 백테스트의 정확도 수치를 갱신한 검증이 아니다.

새 AVM 결과의 비교사례에는 원거래 금액·거래일·면적·층·선정 이유·대상과의 면적 차이를 보존한다.
API 또는 캐시의 최종 성공 관측 시각, 조회 지역 코드·거래 월·엔드포인트와 국토부 공개자료 링크도 남긴다.
`molit-sha256:...`은 조회 조건과 거래 필드의 **서비스 지문**이며 국토부가 발급한 개별 거래 고유번호가 아니다.
정정·취소 또는 동일 조건의 중복 거래를 완전히 식별하는 공식 객체 키로 사용하지 않는다.
새 데이터의 근거는 리포트와 후보 요약에서 확인한다. 기존 결과에 없는 거래 지문·관측일을 현재 시각으로 소급 작성하지 않는다.

### 판독 상태와 문서 근거

문서별 `parsed`·`failed`·`not_supplied`, 전체 `completed`·`partial`·`failed`를 구분한다.
판독 실패·미제공·빈 페이지 때문에 권리 확인이 부족하면 `risk_grade=unknown`, `risk_score=null`로 표시한다.
부분 판독이라도 실제 탐지한 위험 신호는 주의·고위험으로 남긴다. 경고 한 건도 ‘위험 신호 미검출’로 바꾸지 않는다.
위험 신호가 없을 때의 표시는 **판독한 문서 내 위험 신호 미검출**이며 거래 안전의 보증이 아니다.

PDF는 메모리에서 처리하고 원문·전체 추출 텍스트를 저장하지 않는다.
후보에 연결한 기록에는 SHA-256 문서 지문, 페이지 수·빈 페이지, 명시된 발급일,
판단에 사용한 위험 키워드·채권 금액의 최소 발췌와 페이지 번호만 저장한다.
이름·주민번호를 포함한 주변 문장을 저장하지 않는다. 발급일이 없거나 유효한 날짜가 아니면 미확인이며 현재 권리관계·문서 진위는 별도 확인이다.
위험 키워드가 검출되지 않았다는 사실은 특정 페이지에 위험이 없음을 확정한 원문 증거가 아니다.

후보에 연결하면 등기부 소재지와 입력 주소·동·호를 대조한다.
다른 주소·호 또는 대조할 수 없는 문서는 현재 후보가 확인됐다고 표시하지 않는다. 도로명·지번 표기가 달라 일치하지 않는 경우도 사용자의 확인이 필요하다.
분석 도중 후보 입력이 바뀌면 결과 연결을 거부한다. 화면 초기화 때문에 후보 전달 정보가 사라지지 않도록 권리 화면의 페이지 이탈 시점에만 전달 정보를 정리한다.
최소 근거는 기존 분석 요약에 저장하므로 후보의 소유권·삭제·변경 재검토 정책을 따른다.

`tests/test_analysis_provenance.py`는 거래 지문·관측일·원 단위 변환, 최소 발췌·페이지·발급일·빈 페이지·주소/호 불일치를 검사한다.
`tests/test_rights_and_chat.py`는 잘못된 PDF·부분 실패·위험 신호 보존을 검사한다.
브라우저의 `verify_property_evidence_browser.cjs`는 실제 손상 PDF와 가상 텍스트 PDF를 API로 판독하고 후보에 저장한 근거를 새로고침 후 확인한다.
실제 발급 문서의 다양한 레이아웃·말소·OCR 정확도나 새 AVM 정확도 평가는 별도다.

2026-10-02 격리 PostgreSQL·Redis의 전체 회귀 **1,116건 통과·1건 건너뜀**,
Spring 통합·계산·프록시 및 브라우저 **7종·63개 항목**, 고정·가상 입력 평가 **34건**이 통과했다.
프론트 타입·린트·프로덕션 빌드와 내부 명세 확인도 통과했다.
새 흐름은 `./venv-wsl/bin/python scripts/run_spring_tests.py --browser`에 포함한다.
실행 중인 로컬 서비스에는 `node scripts/verify_property_evidence_browser.cjs`로 검증용 계정을 생성하고 종료 시 삭제한다.
JSON·화면 증거는 `evaluation-results/property-evidence-browser*.json`·`property-evidence-browser*.png`에 남는다.
같은 날 Docker 반영 후 실제 웹 3002에서도 새 흐름 7개 항목이 통과했다. 격리 결과는 `property-evidence-browser-isolated.json`으로 보존한다.
로컬 결과를 원격 CI 실행 완료나 실제 발급 문서 탐지 정확도로 설명하지 않는다.

## 자금 입력과 계산·저장 기준

화면·대화·케이스 비교가 같은 자금 조건으로 계산하도록 주택 수 기준과 공통 조건 전달을 통일했다. 이 문서는 입력 의미, 이전 결과를 확인하는 방법과 검증 범위를 설명한다.

<a id="funding-input-입력-기준"></a>

### 입력 기준

- `owned_homes`는 이번 취득을 포함한 **취득 후 주택 수**이며 1~100의 정수다. 일반적인 첫 주택 취득은 1, 기존 1주택을 유지하며 추가 취득하면 2로 입력한다.
- 케이스의 `cash_available`은 총 보유 현금이다. 화면·대화·시나리오에 공통 조건을 적용할 때 `emergency_reserve`를 한 번 차감한다.
- 개별 자금 분석에서 지정한 현금은 매수에 쓸 수 있는 금액이다. 저장한 분석을 복원하거나 대화에서 이 금액을 별도로 지정하면 비상자금을 다시 차감하지 않는다.
- 연소득 0은 입력 가능하지만 DSR을 확인한 것으로 처리하지 않는다. 소득 확인 안내가 남는다.

취득하는 주택을 포함해 산정하는 일반 원칙은 [국가법령정보센터 지방세법 시행령 제28조의4](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=04&joNo=0028&lsiSeq=288831&urlMode=lsScJoRltInfoR)에서 확인했다. 해당 조문에는 주택 수 산정 제외 등 예외가 있으며, 이 기능이 세대 구성·입주권·분양권·오피스텔·특례를 자동 판정하지는 않는다.

<a id="funding-input-화면과-계산-경로"></a>

### 화면과 계산 경로

후보 상세의 **자금 분석**과 다음 행동의 **분석으로 이동**은 같은 시드 생성 함수를 사용한다. 기존 분석이 없으면 공통 매수 조건을 채운다. 기존 분석이 있으면 저장한 개별 조건을 우선하며, **공통 자금 조건 적용**을 누르면 현금·주택 수·금리·대출 기간 등의 공통 값을 다시 채운다. 공통 조건에 없는 값은 계산기의 기본값 또는 미입력으로 돌아가므로 실행 전에 확인해야 한다.

공개 `POST /api/simulation`은 Kotlin이 입력·계산·후보 저장을 처리한다. 대화의 `execute_simulation()`과 케이스 시나리오도 내부 계약으로 같은 Kotlin 계산기를 호출한다. Python은 공통 조건 변환과 리포트 표현을 유지하며 공통 조건 변환은 `profile_funding_inputs()`로 통일했다. 새 결과와 후보 자금 요약에는 `home_count_basis: after_purchase`, 계산 엔진·계산 버전·세율 기준일을 기록한다. 리포트에도 주택 수를 표시한다.

후보에 연결하는 계산은 현재 저장된 후보 가격과 계산 가격이 같아야 한다. 후보 가격이 없거나 다르면
보고서 호출 전에 422로 거부하며, 먼저 후보 가격을 확인·갱신해야 한다. 후보를 지정하지 않은 독립 계산은
기존대로 가능하다. 보고서 생성 중 후보가 변경되면 저장 단계에서 다시 거부한다. 내부 분석 저장도
가격이 등록된 후보에는 다른 가격이나 가격 누락 결과를 연결하지 않는다. 가격 없는 과거 내부 기록의
호환성은 유지하지만 의사결정 평가에서 미확인으로 구분하며, 이 변경으로 기존 자료를 자동 재계산하지 않는다.

이전 결과는 자동으로 1을 더하거나 다시 계산하지 않는다. 과거 화면의 ‘취득 전’ 표시를 보고 입력했을 가능성을 코드만으로 판별할 수 없다. 기준 기록이 없는 저장 결과를 자금 화면에서 열면 이번 취득을 포함한 수인지 재확인하도록 안내한다. 계산 결과의 추가 필드는 이전 결과를 읽을 때 생략 가능하므로 DB 마이그레이션은 필요 없다.

<a id="funding-input-검증-방법"></a>

### 검증 방법

- Kotlin `FundingPersistenceIT`: 실제 Spring·전용 PostgreSQL·Redis에서 계산 결과/입력 조건 저장, 타인 후보 404,
  가격 불일치 422, 보고서 생성 도중 가격 변경, 내부 연결의 가격 누락·불일치와 저장 롤백을 검증한다.
  외부 보고서만 대역이며 고정 수식 계산·권한·저장은 실제 구현이다. 실행은 `sh scripts/run_platform_tests.sh`다.
- `tests/test_funding_consistency.py`: 1·2·3주택으로 실제 API·대화 도구·케이스 시나리오를 실행하고 취득 비용·필요 현금·월 상환액·입력 조건·저장 요약을 대조한다. 비상자금 중복 차감, 잘못된 주택 수, 소득 0의 미검증 상태도 확인한다.
- `scripts/verify_candidate_funding_browser.cjs`: 임시 계정을 만들어 후보 → 공통 조건 자동 채움 → 실제 계산 → 시나리오 대조 → 경고 표시 → 새로고침 복원 → 공통 조건 재적용 → 재계산 → 가격 변경 재검토 → 요약의 다음 행동까지 확인하고 계정을 삭제한다.
- CI의 격리 PostgreSQL·Redis 환경에서도 위 브라우저 검증을 실행하도록 추가했다. CI의 실제 원격 실행 결과는 로컬 실행과 별도로 확인해야 한다.

로컬 백엔드는 반드시 `./venv-wsl/bin/python scripts/run_isolated_tests.py tests/ -q`로 실행한다. 브라우저는 실행 중인 서비스에 `node scripts/verify_candidate_funding_browser.cjs`, 또는 격리 API에 `node scripts/verify_candidate_funding_browser.cjs http://127.0.0.1:8000`으로 실행한다. 기본 서비스 주소는 `http://localhost:3002`이며 `E2E_BASE_URL`로 바꿀 수 있다.

브라우저 결과는 `evaluation-results/funding-browser-result.json`과 `funding-browser.png`, 개발 프론트엔드를 띄우는 CI 방식은 `funding-browser-ci-result.json`과 `funding-browser-ci.png`, 전체 테스트 결과는 `funding-backend-junit.xml`에 보관한다.

검증 대상은 입력 전달과 현재 계산 모델의 결과 일치다. 실제 매물 호가, 최신 세율의 모든 예외, 금융기관 대출 승인, 실제 LLM의 자연어 추출 정확도까지 검증했다는 의미는 아니다.

## 화면 이동과 다음 행동

제품의 중심 흐름은 **관심 매물 등록 → 케이스 후보 → 분석 → 매수 검토 요약 → 비교·사용자 선택 → 다음 행동·변경 재검토**다. 사용자가 이미 찾은 매물을 `/listings`에서 직접 등록해 시작할 수 있다. 동네 탐색과 외부 지도 검색은 매물을 찾는 보조 경로다. 현재 화면의 탐색 단계 안내는 `동네 탐색 → 매물 보관함 → 후보 검토·비교`를 제공하며, 홈의 후보 비교는 `/cases`로 연결한다. `/comparison`은 추천 화면의 가상 매물 바구니를 사용하는 추가 도구이므로 `샘플 매물 비교`로 표시한다.

동네 탐색의 외부 버튼은 네이버 부동산 지도 검색을 새 탭으로 연다. 단지명을 주소에 덧붙이지 않고 확인한 도로명주소(없으면 지번주소)를 검색어로 전달한다. 검색 주소를 표시하고 복사 버튼을 제공하므로 외부 검색창 자동 입력이 안 되면 사용자가 붙여넣어 검색할 수 있다. 후보 직접 입력에서 상세 주소를 수정하면 외부 검색과 등록 이동에도 수정한 주소를 사용한다. 개별 매물이나 단지번호를 자동 식별해 선택하는 기능은 아니며, 네이버 검색 결과와 가격·거래 필터는 사용자가 확인한다.

최종 추천 단지는 카카오 로컬 API로 상세 주소를 조회한다. 아파트 카테고리·단지명(차수·번호 보존)·법정동을 대조하고, 주소 검색의 시군구코드와 지번이 일치할 때만 연결한다. 도로명과 지번을 각각 표시하고 각각의 네이버 지도 검색 링크를 제공한다. 출처와 조회일도 표시하며, 주소 미확인·다중 후보는 추측으로 채우지 않는다. API 장애에도 실거래 추천은 유지된다. 일치 결과는 기존 PostgreSQL API 캐시에 7일, 미일치는 1시간 보관하며 네트워크 오류는 캐시하지 않는다. 거래 집계에서도 동이 다른 동명 단지를 합치지 않는다.

상세 주소 조회는 현재 매물 존재 여부를 확인하는 기능이 아니다. 지도에서 단지 위치를 확인한 뒤 네이버 부동산의 활성 매물·거래 조건은 별도로 확인해야 한다.

2026-09-25 실조회: 노원구 최근 6개월 추천 5개 중 4개의 도로명·지번이 일치했다. 네이버 지도에서 `서울 노원구 덕릉로 780` 검색 링크를 실제로 열어 검색창 입력, `동아불암아파트`, 지번 `상계동 1285` 표시를 확인했다. 이 검증은 해당 주소 1건의 지도 연결 확인이며 전체 단지의 주소 정확도나 실시간 매물 재고를 보증하지 않는다.

`이 단지 매물 등록`은 단지명·주소·유형·선택한 케이스를 `/listings`의 검색 매개변수로 전달한다. 서버에서 문자열 길이·유형·ID 형식을 검사하며, 실제 케이스·매물 소유권은 API에서 확인한다. 새로고침과 단계 이동에도 케이스를 유지한다. 거래 집계의 평균 면적·가격은 개별 매물 입력값으로 복사하지 않는다. 링크 없이 후보를 저장할 때도 실제 검토 면적을 직접 입력한다.

보관함의 등록 폼과 CSV 입력은 펼침 영역에 두고, 등록 완료 후 저장된 매물 목록으로 안내한다. 단지 정보와 함께 진입하면 등록 폼을 펼쳐 둔다. 케이스의 원본 확인 링크는 `listing_id`를 전달하여 해당 매물만 표시한다. 단건 조회 API는 본인 매물만 반환하고 타인·없는 매물은 404로 처리한다.

### 매수 검토 요약과 다음 행동

케이스의 **매수 검토 요약**(`/cases/{id}/summary`)은 후보별 적합성·가격성·자금성·위험성·실행성을 같은 기준으로 표시한다. 사용 값·출처·기준일·이전 근거·누락 정보를 확인하고 공통 매수 조건·시세추정·자금·권리·체크리스트·거래 준비 화면으로 이동한다. API 계약과 확인 기준은 [의사결정 문서](#decision-assessment)를 따른다.

자금 화면에는 현재 후보 가격·유형과 저장된 개별 자금 조건을 전달한다. 공통 조건으로 재계산하려면 사용자가 **공통 자금 조건 적용**을 선택한다. 취득 후 주택 수와 비상자금 적용은 [자금 입력 기준](#funding-input)을 따른다.

후보 비교는 `/cases/{id}/comparison`에서 실제 사용자 후보를 대상으로 한다. 미확인 후보를 선택해도 검토 완료로 바꾸지 않고 보완 필요 표시를 유지한다. 가격·원본 상태가 바뀌면 이전 분석을 현재 금액으로 사용하지 않으며 새로고침 후에도 후보·선택·저장 입력과 재검토 상태를 유지한다. 선택 이유와 거래 준비 작업은 `/cases/{id}/execution`으로 연결한다.

### 검증

- `tests/test_listing_import.py`: 단건 조회의 인증·소유권·가격 값을 기존 회귀 시나리오에서 확인한다.
- `scripts/verify_listing_import_browser.cjs`: 실제 API와 DB를 사용한 등록·원본 변경·재검토·재선택 흐름. 원문 수집 응답만 고정 입력이다.
- `scripts/verify_navigation_browser.cjs <격리 API 주소>`: 시장 집계·단지 추천은 고정 입력, 인증·매물 등록·후보 저장·원본 변경은 실제 API로 실행한다. 외부 링크 주소, 입력 전달, 새로고침, 케이스 유지, 원본 딥링크, 홈·모바일 메뉴와 가로 넘침을 검사한다. 네이버가 실제 반환하는 검색 결과와 AVM 품질은 이 검사의 범위 밖이다.
- `scripts/verify_candidate_funding_browser.cjs`: 후보 입력 전달·실제 자금 계산·저장 조건 복원·공통 조건 적용·새로고침을 확인한다.
- `scripts/verify_decision_assessment_browser.cjs`: 다섯 판단 축·근거·현재 비교 금액, 실제 자금 계산·저장, 가격 변경 후 재검토, 사용자 선택·복원과 좁은 웹 화면을 확인한다. 실제 AVM과 문서 판독 품질 평가와는 구분한다.

브라우저 검증은 임시 계정을 생성하고 종료 시 삭제한다. JSON 결과와 데스크톱·좁은 웹 화면 이미지는 `evaluation-results/navigation-*`·`funding-browser*`·`assessment-browser*`에 남기며 CI 아티팩트로 보관한다. 모바일 앱 구현이나 검증을 의미하지 않는다. 최신 구현과 다음 작업은 [인수인계](../project-handoff.md)를 따른다.
