## 다섯 판단 축과 검토 기준

매수 케이스의 **매수 검토 요약**에서 후보별 적합성·가격성·자금성·위험성·실행성을 확인한다. 각 축은 사용한 값·출처·기준 시각과 부족한 정보를 보여주고, 해당 입력·분석·검토 화면으로 연결한다. 후보 선택은 사용자가 한다.

<a id="decision-assessment-이용-흐름"></a>

### 이용 흐름

1. 매물 보관함에 관심 매물의 URL 또는 직접 확인한 값을 등록하고 매수 케이스에 후보로 저장한다.
2. 케이스에서 예산과 공통 매수 조건을 입력하고 후보별 시세·자금·권리 분석을 실행한다.
3. **매수 검토 요약**에서 후보별 확인 상태와 판단 근거를 비교한다.
4. 다음 행동으로 부족한 입력·서류·현장 확인을 보완한다. 후보 비교에서 선택 이유를 저장하면 거래 준비 작업으로 이어진다.

포털의 매물 추출 성공은 필수 조건이 아니다. 직접 입력한 후보도 검토할 수 있으나 출처·확인 시각을 연결하지 않으면 미확인 사항으로 남는다.

<a id="decision-assessment-판단-축과-표시-기준"></a>

### 판단 축과 표시 기준

| 축 | 사용하는 자료 | 현재 표시 기준 |
|---|---|---|
| 적합성 | 예산, 면적, 물건 유형, 관심 지역의 법정동 코드 | 설정된 조건만 비교한다. 후보의 준공연도가 없으면 연식 조건은 미확인이다. 지역 이름만으로 법정동을 추정하지 않는다. |
| 가격성 | 희망가, 저장된 AVM 추정가·신뢰도·비교사례 수 | 유효한 기준일, 양수 가격, 신뢰도 50% 이상 및 100% 이하, 비교사례가 있을 때 가격 차이를 계산한다. 희망가가 추정가보다 5% 넘게 높으면 재검토를 안내한다. 이 값은 서비스의 확인 기준이며 적정 매수가격이나 정확도 보장이 아니다. |
| 자금성 | 후보 가격과 저장된 계산 결과·입력 조건 | 현재 가격으로 계산했는지, 취득 후 주택 수가 기록됐는지, 현금·첫 달 상환액·소득 등 필요한 기준이 있는지 확인한다. 현금 부족·상환 부담·계산기에 적용된 대출 기준 초과는 주의로 표시한다. |
| 위험성 | 업로드 문서의 판독 결과와 위험 신호, 매물 출처 확인 | 등기부·건축물대장 판독 여부를 업로드 여부와 구분한다. 둘 다 판독되지 않았거나 원본 확인 시각이 없으면 검토 완료로 표시하지 않는다. 과거 위험 신호는 만료 후에도 재확인 대상으로 남긴다. |
| 실행성 | 위 네 축, 체크리스트와 다음 행동, 사용자 선택 기록 | 네 축의 근거와 등록된 확인 항목이 모두 해결된 경우에만 등록 검토 항목 확인으로 표시한다. 체크리스트 완료율을 추천 점수로 사용하지 않는다. |

상태는 `등록 자료 확인`, `주의·재검토`, `미확인`, `갱신 필요`, `분석 실패`, `분석 중`을 구분한다. ‘등록 자료 확인’은 저장된 자료로 해당 기준을 비교할 수 있다는 뜻이며 거래 안전성의 인증이 아니다.

매물 원본 변경·재확인 필요, 분석 만료·기준일 누락·미래 시각, 후보 가격과 자금 분석 가격의 불일치가 있으면 이전 결과를 현재 비교 금액에 사용하지 않는다. 과거 값은 근거에서 이전·미확인 값으로 구분해 볼 수 있다. 기준 시각을 모르는 자료에 조회 시각을 임의로 채우지 않는다.

<a id="decision-assessment-구현-계약"></a>

### 구현 계약

`GET /api/cases/{id}/summary`는 소유자 확인 후 `case`, `comparison`, `decision`을 반환한다. `decision`은 버전·조회 시각·후보별 다섯 축·현재 사용 가능한 비교 금액·다음 행동·결과의 한계를 포함한다. 각 근거의 출처는 사용자 입력·계산 결과·문서 분석·작업 기록으로 구분한다.

`services/intelligence/backend/services/case_decision_assessment.py`가 같은 케이스 자료에서 결과를 계산한다. 후보 비교도 이 결과의 검토 완료 여부와 가격 차이를 사용한다. 조회 중 외부 API·LLM·새 작업을 실행하거나 선택 상태를 변경하지 않는다. 별도 테이블이나 데이터 이관 없이 기존 후보·분석·체크리스트를 사용한다.

자금 분석은 후보에 저장된 개별 입력을 사용하며 공통 조건과 다르다는 이유만으로 무효화하지 않는다. 재계산 화면에서는 저장된 입력과 공통 조건 적용을 선택할 수 있다. 권리 원문 PDF는 기존처럼 저장하지 않으며 판독 성공 여부만 요약에 추가한다. 이전 권리 결과에 이 기록이 없으면 다시 분석해야 한다.

<a id="decision-assessment-검증-범위"></a>

### 검증 범위

- `tests/test_case_decision_assessment.py`: 다섯 축의 근거, 상태 구분, 기준일 누락·미래 시각·만료, 원본 변경, 가격 차이, 자금 입력 부족, 판독 실패, 법정동 범위와 자동 선택 방지를 확인한다.
- `tests/test_purchase_cases.py`: 실제 API의 소유자 격리, 조회 후 상태 보존, 판독할 수 없는 PDF의 확인 상태를 검증한다.
- `services/intelligence/evaluation/datasets/decision.json`: 고정 시각의 가상 케이스를 재생한다. 비교사례 수·문서 판독·취득 후 주택 수·매물 확인 시각은 선언된 검증용 입력이며 실제 매물 또는 문서 판독 실적이 아니다.
- `scripts/verify_decision_assessment_browser.cjs`: 실제 자금 계산·후보 저장, 다섯 축 표시·근거 확인, 조건 전달, 가격 수정 후 재검토, 새로고침 복원, 미확인 상태에서 사용자 선택, 좁은 웹 화면을 확인하고 임시 계정을 삭제한다.

브라우저 결과는 `evaluation-results/assessment-browser*.json`과 화면 이미지에 저장한다. CI에도 이 흐름과 아티팩트 보관을 추가했다. 실행 중인 서비스에는 `node scripts/verify_decision_assessment_browser.cjs`, 개발 프론트엔드를 따로 띄울 때는 명령 뒤에 API 주소를 전달한다.

2026년 10월 1일 격리 DB·Redis에서 백엔드 전체 테스트 1,065건이 통과했고 1건은 건너뛰었다. 프론트엔드 타입·린트·프로덕션 빌드와 Docker 재빌드가 통과했다. 실제 Docker 서비스와 로컬 개발 프론트엔드에서 통합 의사결정 브라우저 검증 13개 항목이 각각 통과했으며 임시 계정 삭제 응답은 모두 200이었다. 기존 자금 브라우저 검증 13개 항목과 화면 이동 검증 7개 항목도 통과했다. 로컬 개발 프론트엔드 검증은 로컬 API에 연결했으며 원격 GitHub Actions 실행 완료를 의미하지 않는다.

이 검증은 저장된 근거를 올바르게 연결하고 불확실성을 표시하는지 확인한다. 실제 AVM 정확도, 문서 위험 신호 탐지 정확도, 실호가·매물 존재, 최신 세금·금융 규칙의 전체 예외, 사용자 투자 성과를 보장하지 않는다. 통근·학군·소음·주차 자료, 문서 발급일·페이지별 근거와 부동산 객체의 완전한 동일성은 후속 작업이다. 모바일 앱 개발은 이후 단계로 둔다.

## 자금 입력과 계산·저장 기준

화면·대화·케이스 비교가 같은 자금 조건으로 계산하도록 주택 수 기준과 공통 조건 전달을 통일했다. 이 문서는 입력 의미, 이전 결과를 확인하는 방법과 검증 범위를 설명한다.

<a id="funding-input-입력-기준"></a>

### 입력 기준

- `owned_homes`는 이번 취득을 포함한 **취득 후 주택 수**이며 1~100의 정수다. 일반적인 첫 주택 취득은 1, 기존 1주택을 유지하며 추가 취득하면 2로 입력한다.
- 케이스의 `cash_available`은 총 보유 현금이다. 화면·대화·시나리오에 공통 조건을 적용할 때 `emergency_reserve`를 한 번 차감한다.
- 개별 자금 분석에서 지정한 현금은 매수에 쓸 수 있는 금액이다. 저장한 분석을 복원하거나 대화에서 이 금액을 별도로 지정하면 비상자금을 다시 차감하지 않는다.
- 연소득 0은 입력 가능하지만 DSR을 확인한 것으로 처리하지 않는다. 소득 확인 안내가 남는다.

취득하는 주택을 포함해 산정하는 일반 원칙은 [국가법령정보센터 지방세법 시행령 제28조의4](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=04&joNo=0028&lsiSeq=288831&urlMode=lsScJoRltInfoR)에서 확인했다. 해당 조문에는 주택 수 산정 제외 등 예외가 있으며, 이 기능이 세대 구성·입주권·분양권·오피스텔·특례를 자동 판정하지는 않는다.

<a id="funding-input-화면과-계산-경로"></a>

### 화면과 계산 경로

후보 상세의 **자금 분석**과 다음 행동의 **분석으로 이동**은 같은 시드 생성 함수를 사용한다. 기존 분석이 없으면 공통 매수 조건을 채운다. 기존 분석이 있으면 저장한 개별 조건을 우선하며, **공통 자금 조건 적용**을 누르면 현금·주택 수·금리·대출 기간 등의 공통 값을 다시 채운다. 공통 조건에 없는 값은 계산기의 기본값 또는 미입력으로 돌아가므로 실행 전에 확인해야 한다.

공개 `POST /api/simulation`은 Kotlin이 입력·계산·후보 저장을 처리한다. 대화의 `execute_simulation()`과 케이스 시나리오도 내부 계약으로 같은 Kotlin 계산기를 호출한다. Python은 공통 조건 변환과 리포트 표현을 유지하며 공통 조건 변환은 `profile_funding_inputs()`로 통일했다. 새 결과와 후보 자금 요약에는 `home_count_basis: after_purchase`, 계산 엔진·계산 버전·세율 기준일을 기록한다. 리포트에도 주택 수를 표시한다.

이전 결과는 자동으로 1을 더하거나 다시 계산하지 않는다. 과거 화면의 ‘취득 전’ 표시를 보고 입력했을 가능성을 코드만으로 판별할 수 없다. 기준 기록이 없는 저장 결과를 자금 화면에서 열면 이번 취득을 포함한 수인지 재확인하도록 안내한다. 계산 결과의 추가 필드는 이전 결과를 읽을 때 생략 가능하므로 DB 마이그레이션은 필요 없다.

<a id="funding-input-검증-방법"></a>

### 검증 방법

- `tests/test_funding_consistency.py`: 1·2·3주택으로 실제 API·대화 도구·케이스 시나리오를 실행하고 취득 비용·필요 현금·월 상환액·입력 조건·저장 요약을 대조한다. 비상자금 중복 차감, 잘못된 주택 수, 소득 0의 미검증 상태도 확인한다.
- `scripts/verify_candidate_funding_browser.cjs`: 임시 계정을 만들어 후보 → 공통 조건 자동 채움 → 실제 계산 → 시나리오 대조 → 경고 표시 → 새로고침 복원 → 공통 조건 재적용 → 재계산 → 가격 변경 재검토 → 요약의 다음 행동까지 확인하고 계정을 삭제한다.
- CI의 격리 PostgreSQL·Redis 환경에서도 위 브라우저 검증을 실행하도록 추가했다. CI의 실제 원격 실행 결과는 로컬 실행과 별도로 확인해야 한다.

로컬 백엔드는 반드시 `./venv-wsl/bin/python scripts/run_isolated_tests.py tests/ -q`로 실행한다. 브라우저는 실행 중인 서비스에 `node scripts/verify_candidate_funding_browser.cjs`, 또는 격리 API에 `node scripts/verify_candidate_funding_browser.cjs http://127.0.0.1:8000`으로 실행한다. 기본 서비스 주소는 `http://localhost:3002`이며 `E2E_BASE_URL`로 바꿀 수 있다.

브라우저 결과는 `evaluation-results/funding-browser-result.json`과 `funding-browser.png`, 개발 프론트엔드를 띄우는 CI 방식은 `funding-browser-ci-result.json`과 `funding-browser-ci.png`, 전체 테스트 결과는 `funding-backend-junit.xml`에 보관한다.

2026년 9월 30일 격리 DB·Redis에서 전체 백엔드 테스트 1,011건이 통과했고 1건은 건너뛰었다. 프론트엔드 타입 검사·린트·프로덕션 빌드와 Docker 재빌드도 통과했다. 2026년 10월 1일 실제 Docker 서비스와 CI 방식의 개발 프론트엔드에서 각각 브라우저 검증 13개 항목이 통과했으며 검증용 계정 삭제 응답은 모두 200이었다. CI 방식 검증도 로컬 API에 연결해 실행했으며 원격 GitHub Actions 실행 완료를 의미하지 않는다.

검증 대상은 입력 전달과 현재 계산 모델의 결과 일치다. 실제 매물 호가, 최신 세율의 모든 예외, 금융기관 대출 승인, 실제 LLM의 자연어 추출 정확도까지 검증했다는 의미는 아니다.

2026-10-01 Kotlin 계산 이전 후 Python 1,092개 통과·1개 건너뜀, Kotlin 단위 18개와 계산 연결 6개,
기존 수식 54개 조건 대조 및 격리 브라우저 자금 13개 항목을 확인했다. [계산 이전 기록](../architecture.md#calculations)을 따른다.

## 화면 이동과 다음 행동

제품의 중심 흐름은 **관심 매물 등록 → 케이스 후보 → 분석 → 매수 검토 요약 → 비교·사용자 선택 → 다음 행동·변경 재검토**다. 사용자가 이미 찾은 매물을 `/listings`에서 직접 등록해 시작할 수 있다. 동네 탐색과 외부 지도 검색은 매물을 찾는 보조 경로다. 현재 화면의 탐색 단계 안내는 `동네 탐색 → 매물 보관함 → 후보 검토·비교`를 제공하며, 홈의 후보 비교는 `/cases`로 연결한다. `/comparison`은 추천 화면의 가상 매물 바구니를 사용하는 추가 도구이므로 `샘플 매물 비교`로 표시한다.

동네 탐색의 외부 버튼은 네이버 부동산 지도 검색을 새 탭으로 연다. 단지명을 주소에 덧붙이지 않고 확인한 도로명주소(없으면 지번주소)를 검색어로 전달한다. 검색 주소를 표시하고 복사 버튼을 제공하므로 외부 검색창 자동 입력이 안 되면 사용자가 붙여넣어 검색할 수 있다. 후보 직접 입력에서 상세 주소를 수정하면 외부 검색과 등록 이동에도 수정한 주소를 사용한다. 개별 매물이나 단지번호를 자동 식별해 선택하는 기능은 아니며, 네이버 검색 결과와 가격·거래 필터는 사용자가 확인한다.

최종 추천 단지는 카카오 로컬 API로 상세 주소를 조회한다. 아파트 카테고리·단지명(차수·번호 보존)·법정동을 대조하고, 주소 검색의 시군구코드와 지번이 일치할 때만 연결한다. 도로명과 지번을 각각 표시하고 각각의 네이버 지도 검색 링크를 제공한다. 출처와 조회일도 표시하며, 주소 미확인·다중 후보는 추측으로 채우지 않는다. API 장애에도 실거래 추천은 유지된다. 일치 결과는 기존 PostgreSQL API 캐시에 7일, 미일치는 1시간 보관하며 네트워크 오류는 캐시하지 않는다. 거래 집계에서도 동이 다른 동명 단지를 합치지 않는다.

상세 주소 조회는 현재 매물 존재 여부를 확인하는 기능이 아니다. 지도에서 단지 위치를 확인한 뒤 네이버 부동산의 활성 매물·거래 조건은 별도로 확인해야 한다.

2026-09-25 실조회: 노원구 최근 6개월 추천 5개 중 4개의 도로명·지번이 일치했다. 네이버 지도에서 `서울 노원구 덕릉로 780` 검색 링크를 실제로 열어 검색창 입력, `동아불암아파트`, 지번 `상계동 1285` 표시를 확인했다. 이 검증은 해당 주소 1건의 지도 연결 확인이며 전체 단지의 주소 정확도나 실시간 매물 재고를 보증하지 않는다.

`이 단지 매물 등록`은 단지명·주소·유형·선택한 케이스를 `/listings`의 검색 매개변수로 전달한다. 서버에서 문자열 길이·유형·ID 형식을 검사하며, 실제 케이스·매물 소유권은 API에서 확인한다. 새로고침과 단계 이동에도 케이스를 유지한다. 거래 집계의 평균 면적·가격은 개별 매물 입력값으로 복사하지 않는다. 링크 없이 후보를 저장할 때도 실제 검토 면적을 직접 입력한다.

보관함의 등록 폼과 CSV 입력은 펼침 영역에 두고, 등록 완료 후 저장된 매물 목록으로 안내한다. 단지 정보와 함께 진입하면 등록 폼을 펼쳐 둔다. 케이스의 원본 확인 링크는 `listing_id`를 전달하여 해당 매물만 표시한다. 단건 조회 API는 본인 매물만 반환하고 타인·없는 매물은 404로 처리한다.

### 매수 검토 요약과 다음 행동

케이스의 **매수 검토 요약**(`/cases/{id}/summary`)은 후보별 적합성·가격성·자금성·위험성·실행성을 같은 기준으로 표시한다. 사용 값·출처·기준일·이전 근거·누락 정보를 확인하고 공통 매수 조건·시세추정·자금·권리·체크리스트·거래 준비 화면으로 이동한다. API 계약과 확인 기준은 [의사결정 문서](#decision-assessment)를 따른다.

자금 화면에는 현재 후보 가격·유형과 저장된 개별 자금 조건을 전달한다. 공통 조건으로 재계산하려면 사용자가 **공통 자금 조건 적용**을 선택한다. 취득 후 주택 수와 비상자금 적용은 [자금 입력 기준](#funding-input)을 따른다.

후보 비교는 `/cases/{id}/comparison`에서 실제 사용자 후보를 대상으로 한다. 미확인 후보를 선택해도 검토 완료로 바꾸지 않고 보완 필요 표시를 유지한다. 가격·원본 상태가 바뀌면 이전 분석을 현재 금액으로 사용하지 않으며 새로고침 후에도 후보·선택·저장 입력과 재검토 상태를 유지한다. 선택 이유와 거래 준비 작업은 `/cases/{id}/execution`으로 연결한다.

### 검증

- `tests/test_listing_import.py`: 단건 조회의 인증·소유권·가격 값을 기존 회귀 시나리오에서 확인한다.
- `scripts/verify_listing_import_browser.cjs`: 실제 API와 DB를 사용한 등록·원본 변경·재검토·재선택 흐름. 원문 수집 응답만 고정 입력이다.
- `scripts/verify_navigation_browser.cjs <격리 API 주소>`: 시장 집계·단지 추천은 고정 입력, 인증·매물 등록·후보 저장·원본 변경은 실제 API로 실행한다. 외부 링크 주소, 입력 전달, 새로고침, 케이스 유지, 원본 딥링크, 홈·모바일 메뉴와 가로 넘침을 검사한다. 네이버가 실제 반환하는 검색 결과와 AVM 품질은 이 검사의 범위 밖이다.
- `scripts/verify_candidate_funding_browser.cjs`: 후보 입력 전달·실제 자금 계산·저장 조건 복원·공통 조건 적용·새로고침을 확인한다.
- `scripts/verify_decision_assessment_browser.cjs`: 다섯 판단 축·근거·현재 비교 금액, 실제 자금 계산·저장, 가격 변경 후 재검토, 사용자 선택·복원과 좁은 웹 화면을 확인한다. 실제 AVM과 문서 판독 품질 평가와는 구분한다.

브라우저 검증은 임시 계정을 생성하고 종료 시 삭제한다. JSON 결과와 데스크톱·좁은 웹 화면 이미지는 `evaluation-results/navigation-*`·`funding-browser*`·`assessment-browser*`에 남기며 CI 아티팩트로 보관한다. 모바일 앱 구현이나 검증을 의미하지 않는다. 최신 구현과 다음 작업은 [인수인계](../project-handoff.md)를 따른다.
