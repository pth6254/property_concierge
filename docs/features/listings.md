## 주소 검색과 별칭

매물 보관함의 직접 등록은 주소 검색부터 시작한다. 검색 결과를 선택하면 확인한 단지·건물명과 지번주소가 자동으로 채워지고 도로명주소·출처·조회 시각을 함께 보여준다. **별칭은 선택 입력**이며 조회한 이름과 따로 저장한다. 별칭을 분석용 건물명이나 단지 매칭 키로 사용하지 않는다.

<a id="address-registration-사용-순서"></a>

### 사용 순서

1. `/listings`에서 매물 등록을 열고 주소·단지명을 검색한다.
2. 도로명·지번과 건물명을 보고 결과를 선택한다. 이름이 없으면 주소를 등록 이름으로 사용하고 건물명 미확인으로 표시한다.
3. 필요하면 `별칭 (선택)`에 나만의 이름을 입력한다. 최대 100자이며 비워도 저장할 수 있다.
4. 주소 선택 후 건축물대장 정보를 확인한다. 여러 건물이면 조회할 건물을 선택한다. 동·호는 각각 선택 입력이며 정확한 호실의 전유면적은 **조회 정보 적용**으로 반영할 수 있다.
5. 유형·면적·가격·정보 확인 일시·거래 상태·출처를 직접 확인해 입력하고 저장한다.
6. 최근 확인·거래 가능·법정동 연결 조건을 충족하는 매매 매물을 케이스 후보로 저장한다. 후보·매수 검토 요약·후보 비교에도 별칭을 따로 표시한다.

네이버 링크 등록과 CSV도 유지한다. 주소 검색이 실패하면 명시적으로 **주소·이름 직접 입력으로 전환**할 수 있다. 이 경로의 이름·주소는 사용자 입력이며 주소 조회로 확인한 자료처럼 표시하지 않는다.

<a id="address-registration-이름주소-확인의-범위"></a>

### 이름·주소 확인의 범위

카카오 주소 결과의 건물명을 우선 사용한다. 단지명 검색의 장소 결과는 주소를 다시 정방향 조회하고, 카페·중개업소 같은 장소 이름을 건물명으로 채택하지 않는다. 건물명이 없으면 건축물대장 기본개요의 시군구·법정동·지번이 일치하는 결과를 대조한다. 조회 범위 안에 이름이 하나일 때만 보완하고 여러 이름이 있거나 조회가 실패하면 미확인으로 남긴다.

검색 결과에 없는 도로명·건물명은 생성하지 않는다. 같은 주소가 같아도 서로 다른 동·호·광고일 수 있으므로 사용자 매물을 임의로 합치지 않는다. 주소 확인은 현재 거래 가능·가격·소유권·개별 호의 동일성을 검증한 결과가 아니다.

<a id="address-registration-저장-계약"></a>

### 저장 계약

`GET /api/listings/address/search?query=...`는 로그인한 사용자에게 구조화한 주소와 1시간 유효한 선택 확인 정보를 반환한다. 서버는 저장 시 서명·사용자·만료와 입력 이름·주소를 검증한다. 이 정보는 로그인 JWT와 별도 형식이며 다른 계정이나 변조한 조회 결과로 확인 출처를 만들 수 없다.

기존 `ImportedListing.payload`에 `alias`와 `address_details`를 저장하고 `ListingRevision` 및 후보 `source_snapshot`에도 보존한다. 주소 조회 증명 자체는 저장하거나 이력에 반환하지 않는다. 법정동 마스터와 주소가 일치해야 하고 API의 시도 약칭은 마스터 이름으로 정규화한다. 기존 CSV에 별칭이 없어도 입력 가능하며 빈 기본값 때문에 이전 자료의 동일 업로드가 상충 갱신으로 바뀌지 않게 한다. 새 DB 테이블·컬럼과 데이터 이관은 필요하지 않다.

`address_details`는 도로명·지번·법정동코드·좌표·건물명·이름 출처·확인 상태·조회 시각·식별 수준을 포함한다. 후보 분석에는 기존의 확인된 등록 이름·주소·면적을 사용하고 별칭은 표시용으로만 전달한다. 저장된 매물·후보는 새로고침 후 복원되며 작성 중인 등록 폼의 임시 복원은 이번 범위에 포함하지 않는다.

<a id="address-registration-검증"></a>

### 검증

- `tests/test_listing_address.py`: 이름·별칭 분리, 선택 필드 생략과 쉼표·따옴표, 주소 정규화·후보·이력, 변조·타인·만료·인증 토큰 오용 차단, 이름 누락·다중 결과·장소명 오인·공급자 실패를 확인한다.
- `scripts/verify_listing_address_browser.cjs`: 서명된 가상 주소 응답을 사용하고 실제 등록 API·DB·후보·매수 검토 요약·새로고침·390px 웹 화면을 확인한다. 임시 계정은 종료 시 삭제한다.
- `scripts/listing_address_browser_fixture.py`는 로컬 검증 계정에 연결한 가상 입력 생성기다. 운영 API에 테스트 모드나 우회 경로를 추가하지 않는다. 실주소 정확도 실적과 구분한다.

브라우저 실행은 저장소 루트의 PowerShell에서 `node scripts/verify_listing_address_browser.cjs`다. 개발 프론트엔드를 별도로 실행하려면 뒤에 API 주소를 전달한다. 결과는 `evaluation-results/address-browser*`에 남기며 CI 아티팩트에도 포함한다.

## 건축물대장·선택 동호 조회

토지 유형은 건축물대장 대신 주소 선택 후 **토지 공개정보**를 자동 조회한다.
지목·필지 면적·공시지가·이용계획을 조회 출처와 기준연도별로 표시한다.
현재 대장 면적을 공시지가 기준연도 면적으로 대체하지 않으며 조회 값을 자동으로 입력 면적에 덮어쓰지 않는다.
등록 화면은 미리보기이고 결과 보관은 시세추정 화면의 토지 공개정보 저장을 사용한다.
필지·시점 검증과 실패 처리의 상세 계약은 [토지 공개정보](decision.md#valuation-support)를 따른다.

주소 선택 후 Spring `POST /api/listings/address/building`으로 건축HUB의 표제부·총괄표제부·층별개요·전유공용면적·지역지구구역·오수정화시설을 조회한다.
주소 선택 서명에 포함된 법정동·지번·산 여부만 사용한다. 이전 선택 정보에 지번 식별값이 없으면 재검색을 안내하며 주소 문자열에서 지번을 추정하지 않는다.

### 표시와 적용

- 검색 목록은 건물명·도로명·지번을 보여주고 상세 정보는 주소 선택 후 조회한다.
- 단지·대지 전체, 선택한 건물, 개별 호실, 층별 면적을 구분한다. 구조·사용승인일·층수는 기본 표시하고 면적·건폐율·용적률·주차·승강기·내진·인증은 펼쳐 확인한다.
- **건물 동과 호수는 각각 선택**이다. 동 없는 건물은 호수만 입력하고 호실 없는 매물은 둘 다 생략할 수 있다. 여러 건물이면 첫 결과나 경비실을 대상 건물로 채택하지 않는다.
- 필지·동·호·대장번호를 대조하고 `exposPubuseGbCd=1`의 양수 `area`만 전유면적으로 사용한다. 누락·중복·다중 대장·불완전 페이지는 자동 적용하지 않는다. 공용면적을 더해 광고 공급면적으로 만들지 않는다.
- **조회 정보 적용**을 눌러야 전유면적·면적 기준·제공된 층을 반영한다. 기존 입력과 다르면 차이를 먼저 표시하며 가격·거래 가능 상태는 변경하지 않는다.
- 주소·동·호·유형 변경이나 조회 중 입력 변경은 이전 결과와 저장 확인 정보를 무효화한다. 조회 실패·호실 미확인에도 직접 입력·등록을 유지한다.
- 다가구는 호(가구)별 면적대장 확인을 안내한다. 토지 면적·권리·현재 호가·공실·실내 층고·전력·방향·위반 여부를 이 API로 확인했다고 표시하지 않는다.

사용승인일·허가일·착공일·자료 생성일을 구분하고 생성일을 준공일로 대체하지 않는다. 미제공 면적을 0으로 채우지 않는다.
건폐율·용적률은 기재된 현황이며 최대 허용치가 아니다. 주택가격·부속지번·최신 규제·도면·다가구 호별 면적대장의 별도 자동 연결은 이번 범위에 포함하지 않는다.

### 저장·운영 계약

출처·관측 시각·건물·호실 근거는 기존 `address_details.building_register`에 저장하고 변경 이력·후보 스냅샷에도 보존한다.
사용자 입력 면적과 공식 전유면적의 일치 여부는 별도 기록하며 입력값을 서버에서 덮어쓰지 않는다.
주소·건축물 선택 서명은 서로 다른 형식이고 사용자·필지·동·호·만료를 Spring에서 검증한다. `building_token`은 선택 입력이며 DB·이력·후보에 저장하지 않는다.
조회 자료는 공부상 동·호의 정보이며 현재 광고·소유권·현장 상태의 동일성 확인이 아니다.

공개 자료는 동일 조건으로 Redis에서 15분 캐시하고 실제 자료 조회 시각을 보존한다. 기능별 최대 500행이며 범위 제한을 표시한다.
사용자별 분당 20회 제한을 적용한다. 외부 요청은 DB 트랜잭션 밖에서 실행한다.
`BUILDING_REGISTER_API_ROOT` 기본값은 공식 건축HUB이며 격리 검사에서만 대역 주소를 지정한다. 새 DB 테이블·마이그레이션은 없다.

### 검증

Kotlin `BuildingRegisterTest`는 부속건물·다중 동·호수만 조회·실제 면적 필드·전유공용 구분·중복/누락/불완전 기록·사용승인일·서명과 입력 차이를 검증한다.
`tests/test_building_register.py`는 실제 격리 Spring의 조회·인증·등록·후보·변경 이력·근거 복원을 확인한다.
`scripts/verify_building_register_browser.cjs`는 대역 공급자와 실제 Spring·웹으로 수동 적용·선택 입력·조회 실패·늦은 응답·새로고침·390px 화면을 확인한다.
`scripts/run_spring_tests.py --browser`에 포함하며 개별 실행은 격리 Spring 8013 주소를 전달한다. 실제 국가 API의 전국 정확도·다가구 호별 제공률과 구분한다.

2026-10-02 해당 영역·주소·등록·물건 식별 Python 회귀 43개, Kotlin 전체 단위 35개(신규 10개),
Spring 통합 18개·계산 연결 6개/54조건·프록시 2개가 통과했다. 기존 브라우저 7종·63개와
건축물대장 브라우저 7개 항목, 타입·린트·프로덕션 빌드·계약 명세 검사를 통과했다.
`evaluation-results/building-register-browser.json`은 대역 공급자 기반이며 실제 외부 조회 기록과 구분한다.

Docker의 Spring·AI API·작업 실행기·웹에 반영한 뒤 실제 카카오·건축HUB를 사용해
`서울 노원구 덕릉로 780 / 상계동 1285`의 동아불암아파트를 확인했다. 같은 필지의 14개 건물 중
103동을 직접 선택하고 1106호의 **전유면적 84.9㎡·11층**과 별도 공용 기록을 조회했다.
화면 적용 → 실제 저장 → 새로고침 복원과 390px 표시까지 4개 항목을 통과했고 임시 계정·매물은 삭제했다.
기록은 `evaluation-results/building-register-live-result.json`, 화면은 `building-register-live-form.png`와
`building-register-live-mobile.png`다. **실주소·호실 1건**의 연결 확인이며 전국 제공률·현재 광고·소유권 검증은 아니다.
이 과정에서 원문 API 키의 `+`가 공백으로 바뀌는 오류를 수정했다. 원문/인코딩 키 모두 실제 요청에서
문자가 보존되는지 Kotlin 회귀 검사에 포함했고 주소 이름 보완 경로에도 같은 처리를 적용했다.

## 직접·URL·CSV 등록과 후보 연결

2026-09-22 구현. 실거래 `transactions`, 단지 추천, 개발용 샘플 매물과 분리한 `imported_listings`에 보관한다. 업로드한 사용자만 조회할 수 있다. 2026-09-23 개별 링크의 Playwright 수집·시점 이력을 추가했다. 범위와 검증 한계는 [수집 문서](#listing-collection)를 참조한다. 공급업체 연동·정기 대량 수집은 없다.

<a id="listing-registration-화면과-사용-순서"></a>

### 화면과 사용 순서

직접 등록은 주소 검색 → 결과 선택 → 조회 이름·도로명·지번 확인 → 면적·가격·확인 출처 입력으로 진행한다.
**별칭은 선택 입력**이며 조회한 단지·건물명과 별도로 저장한다. 검색 실패 시 직접 입력으로 전환할 수 있다.
검증·저장 범위는 [주소 기반 등록](#address-registration)을 따른다. 아래는 기존 CSV 대량 등록 경로다.

1. 메뉴의 **매물 보관함**(`/listings`)에서 빈 CSV 템플릿을 내려받는다.
2. 제공받은 자료로 출처와 원본 매물 ID를 정리하고 UTF-8 CSV로 저장한다. 템플릿은 `web/public/templates/listings.csv`에서 관리한다.
3. 출처 이름 입력 → CSV 선택 → 검증·미리보기 → 검증된 자료 저장 순으로 진행한다.
4. 구·법정동·부동산 유형·거래 유형·가격 상한·최신 확인 조건으로 검색한다. 가격 상한은 매매에서는 희망가, 전월세에서는 보증금에 적용한다. 월세 상한 필터는 아직 없다.
5. 법정동이 연결되어 있고 최근 7일 이내 거래 가능으로 확인된 매매 매물은 매수 검토 케이스에 저장할 수 있다. 케이스에서 기존 AVM·자금 분석을 진행한다. 후보는 저장 당시의 값과 원본 매물 버전을 기억한다. 이후 원본 가격·상태가 달라지면 재확인 경고를 표시하며 후보 가격을 자동 갱신하지 않는다.

후보 비교는 AVM 신뢰도·비교사례 수·매칭 수준을 함께 보여준다. 분석 유효기간이 지났거나 신뢰도가 50% 미만이면 추정가와 희망가의 차이를 가격상 장점으로 판정하지 않는다. 50%는 제품의 재확인 경고 기준이며 거래 안전성을 보증하는 기준이 아니다.

본인이 등록한 매물은 컨시어지에서 ‘강남구에 등록한 아파트 매매 매물 찾아줘’처럼 검색할 수 있다. 신규 `search_listing` 의도로 연결하며, 최근 7일·거래 가능 자료만 최대 5건 안내한다. 근거 없는 외부 실시간 매물 조회나 샘플 데이터 대체를 하지 않는다.

<a id="listing-registration-csv-계약"></a>

### CSV 계약

최대 1MB(화면 파일 제한), 본문 100만 글자, 1,000행. 헤더 이름은 아래 영문 식별자를 그대로 사용한다. 오류가 하나라도 있으면 전체 배치를 저장하지 않는다. 미리보기는 처음 20행이다.

| 열 | 형식·의미 |
|---|---|
| external_id | 필수. 출처에서 유지하는 매물 ID |
| name | 필수. 매물 이름 |
| alias | 선택. 사용자 별칭, 최대 100자. 분석용 건물명과 별도 저장 |
| property_type | 필수. apartment, officetel, row_house, detached, non_residential, industrial, land |
| transaction_type | 필수. purchase(매매), lease(전세), rent(월세) |
| address | 필수. 법정동이 포함된 주소 권장 |
| legal_region_code | 선택. 공식 법정 읍·면·동 10자리 코드 |
| area_sqm | 필수. 양수 ㎡ |
| floor | 선택. 층 설명 |
| building_dong | 선택. 건물 동, 최대 30자. 법정동과 다른 값 |
| unit_number | 선택. 호수, 최대 30자. 사용자 입력이며 외부 확인은 아님 |
| area_basis | exclusive(전용), supply(공급), unknown(미확인). 미입력은 unknown |
| asking_price | 매매에 필수. 양수 원 단위 정수 |
| deposit | 전세에 양수, 월세에 0 이상 원 단위 정수 |
| monthly_rent | 월세에 필수. 양수 원 단위 정수 |
| source_url | 선택. HTTP(S) 원문 링크. 서버는 링크를 방문하지 않음 |
| confirmed_at | 필수. 실제 확인 시각. `2026-09-22T10:00:00+09:00` 같은 시간대 포함 형식 |
| status | active(거래 가능), withdrawn(철회), completed(제공자가 확인한 완료), unknown(미확인). 미입력은 unknown |

금액은 쉼표·‘억’·‘만원’ 없이 원 단위 숫자로 입력한다. 예: 7억원 → `700000000`. 숫자만 잘못된 단위로 입력한 경우 실제 의미를 자동 판별할 수 없으므로 미리보기 금액을 확인해야 한다. 임대 매물에 매매가를 넣거나 매매 매물에 보증금·월세를 넣으면 거절한다.

법정동 연결은 현재 DB의 활성 마스터를 사용한다. 코드가 있으면 주소의 법정동 경로와 일치하는지 검증한다. 코드가 없으면 주소의 공식 법정동 이름을 정확히 매칭한다(서울 → 서울특별시 별칭 지원). 직접 등록의 검색·선택 경로는 도로명·지번·법정동·좌표와 건물명 근거를 연결한다. 일반 CSV의 주소를 외부 조회로 자동 보완하지는 않는다. 연결이 안 된 주소는 주의 표시와 함께 저장하되 지역 필터·후보 저장에서 제외한다.

<a id="listing-registration-갱신출처상태"></a>

### 갱신·출처·상태

- 유일 키는 `(사용자 ID, 출처 이름, 원본 매물 ID)`이다. 주소·면적이 같아도 서로 다른 출처의 매물은 임의로 합치지 않는다.
- 동일 자료 재업로드는 이력을 늘리지 않는다. 더 최신 확인 시각의 자료는 내용을 갱신하고 `listing_revisions`에 기록한다. 이전 버전도 남는다.
- 더 오래된 자료는 제외한다. 같은 확인 시각인데 내용이 다르면 배치 전체를 롤백한다.
- 확인일이 7일을 넘으면 표시상 ‘확인 필요’가 된다. DB 상태를 완료로 변경하지 않는다. 수집 실패·새 파일에서 사라짐·오래됨만으로 완료·철회 처리하지 않는다.
- CSV 상태·확인일은 제공자의 주장이다. 플랫폼이 매물 존재를 독립 검증했다는 의미가 아니다.
- 이력 API는 최신 100건을 반환한다. 계정 탈퇴 시 매물과 이력은 FK CASCADE로 삭제된다.

<a id="listing-registration-api마이그레이션"></a>

### API·마이그레이션

- `POST /api/listings/import`: `{source_name, csv_text, commit:false}`로 검증, `commit:true`로 재검증 후 저장.
- `GET /api/listings`: 페이지당 기본 20건(최대 100건). region_code, property_type, transaction_type, status, budget_max(원), area_min(㎡), fresh_only, page, page_size 필터.
- `GET /api/listings/{id}/history`: 본인 매물 이력. 타 사용자 자료는 404.
- `GET /api/listings/{id}/timeline`: 저장한 확인값 이력과 원문 수집 시도를 나눈 요약(아래 매물 타임라인). 본인 자료만, 타인은 404.
- `GET /api/listings/{id}/market-overlay`: 타임라인에 겹쳐 볼 동일 단지 실거래와 저장된 AVM(아래 실거래·AVM 겹쳐 보기). 본인 자료만, 타인은 404.
- `POST /api/listings/{id}/candidate`: `{case_id}`. 본인 매물과 본인 케이스를 검증하고 서버의 매물 값을 후보로 저장. 전세·월세는 현재 매수 케이스로 변환하지 않음.

실제 환경 적용 전에 `alembic -c services/intelligence/alembic.ini upgrade head`를 실행한다. 신규 리비전은 `k0b1d2e3f456`. 새 테이블 2개만 추가하며 기존 실거래·RAG 테이블을 변경하지 않는다. 운영 Docker의 기존 Alembic 선행 기동 순서를 유지한다.

현재 Docker에는 다른 프로젝트 서비스만 실행 중이어서 그 컨테이너·DB를 사용하지 않고 임시 PostgreSQL·Redis로 검증했다. 이 기능이 운영 DB에 적용됐거나 실제 매물 자료가 적재됐다는 의미는 아니다.

<a id="listing-registration-외부-매물-탐색과-링크-등록"></a>

### 외부 매물 탐색과 링크 등록

- 동네 탐색·챗봇 단지 카드의 ‘네이버페이 부동산에서 매물 보기’는 공식 홈을 새 탭으로 연다. 지역·단지 검색어 복사를 제공하며 외부 검색 조건 자동 적용은 지원하지 않는다.
- `/listings`의 ‘관심 매물 링크 등록’에서 개별 매물 URL과 사용자가 확인한 주소·면적·호가·확인 일시를 입력한다. 상단 원문 수집에서 추출값을 적용할 수도 있다. 페이지 표시값 수집은 실제 거래 가능·가격의 정확성을 보증하지 않는다.
- 지원 링크는 네이버 부동산 호스트의 HTTPS `/articles/숫자` 또는 `articleNo=숫자` 형식이다. 검색 화면 링크는 등록하지 않는다.
- 동일 사용자·네이버 출처·매물 번호는 기존 갱신 규칙을 따른다. 거래 상태 기본값은 미확인이다. 후보 저장 조건은 기존과 동일하다.
- CSV는 ‘여러 매물 등록 (CSV)’를 펼쳐 사용하는 보조 기능이다.

<a id="listing-registration-연결-후보의-원본-변경-재검토-2026-09-24"></a>

### 연결 후보의 원본 변경 재검토 (2026-09-24)

연결된 후보는 저장 당시 원본 버전과 가격·주소·면적·유형·상태를 비교한다. 사용자가 최신 원본을 확인한 뒤 후보 화면의 **확인한 변경사항 반영**을 누르면, 확인했던 리비전과 시각을 다시 대조해 그 사이 원본이 바뀐 경우 반영을 거절한다. 거래 가능·최근 확인·법정동 연결·매매 유형 조건도 재검사한다.

반영한 변경이 분석 입력에 영향을 주면 시세·자금·권리 분석을 `stale`로 돌린다. 이미 최종 선택한 후보라면 선택을 해제하고 이전 가격·분석·선택 근거·실행 항목을 변경 이력에 보존한다. 분석을 다시 확인해야 재선택할 수 있다. 원본이 철회됐거나 확인 시각이 만료됐다면 반영 버튼을 제공하지 않고 원본 재확인을 안내한다.

API는 `POST /api/cases/{case_id}/properties/{property_id}/source-update`이며 본인 케이스·후보·원본만 수정한다. 요청에는 `expected_revision_id`와 `expected_confirmed_at`이 필요하다. 격리 API 통합 테스트와 브라우저 흐름은 `services/intelligence/evaluation/README.md`의 거래 의사결정 게이트를 참고한다.


<a id="property-identity"></a>

## 동·호·층과 면적 기준

직접 매물 등록과 케이스 후보 추가에서 **건물 동·호수·층은 선택 입력**으로 받는다.
면적 기준은 전용·공급·미확인으로 구분한다. 기본 주소 검색은 건물·단지 수준의 확인이다.
별도 건축물대장 조회에서 건물을 선택하면 제공된 동을 채울 수 있고, 입력한 호실의 전유면적·층은
명시적으로 적용한다. 공부상 호실 자료와 현재 광고·소유자·현장 물건의 동일성은 구분한다.
보관함·후보·비교·매수 검토 요약에 같은 정보와 사용자 입력 출처를 표시한다.

CSV에는 `building_dong`, `unit_number`, `area_basis`를 추가할 수 있으며 이전 템플릿도 유효하다.
데이터는 기존 매물 `payload`와 후보 `source_snapshot`의 `identity`에 저장한다. 새 Property 테이블이나 주소 기반 병합을 도입하지 않았다.
주소·면적이 같아도 서로 다른 원본 광고 ID는 별개로 유지한다. 동·호 입력이 같다는 이유로 다른 광고를 같은 호라고 확정하지 않는다.

직접 만든 후보는 카드의 **동·호·층 정보 수정**으로 변경할 수 있다.
보관함에서 가져온 후보는 같은 출처·원본 ID로 더 최신 확인 시각의 자료를 재등록한 뒤 **확인한 변경사항 반영**을 사용한다.
물건 정보가 바뀌면 이전 스냅샷·분석·선택·거래 준비 기록을 보존하고 현재 분석을 만료시킨다. 선택된 후보였다면 선택을 해제해 재검토한다.
실행 도중 동·호 또는 입력이 바뀐 분석도 이전 후보 조건에 연결하지 않는다.

공급면적으로 등록된 후보는 해당 값을 전용면적처럼 AVM에 넘길 수 없다. 전용면적과 면적 기준을 확인한 뒤 다시 실행해야 한다.
기존 자료의 미확인 면적 기준을 자동으로 전용으로 바꾸지는 않는다. 입력된 층을 보존하는 것과 AVM이 모든 경로에서 층 보정을 적용하는 것도 별개다.

회귀 검증은 `tests/test_property_identity.py`, 화면 검증은 `scripts/verify_property_evidence_browser.cjs`다.
사용자 입력 보존·다른 호 분리·기존 CSV 호환·소유권·변경 후 재검토·공급면적 AVM 차단을 확인한다.
정확한 외부 객체 ID, 등기 진위, 소유자나 개별 호의 동일성을 공식 자료로 검증한 결과는 아니다.

## 원문 수집과 시점·상태 관리

### 매물 타임라인 (2026-10-08)

`ListingTimeline`(Kotlin)이 기존 `listing_revisions`(사용자가 저장한 확인값)와 `listing_observations`(원문 수집 시도)에서 읽기 전용으로 만든다.
새 테이블·외부 호출·상태 변경이 없다. 결과는 두 흐름을 섞지 않는다.

- 가격 요약: 거래 유형별로 매매 `asking_price`, 전세 `deposit`, 월세 `deposit`·`monthly_rent`의 최초 값·현재 값·저장값이 바뀐 횟수·최저/최고·누적 변화율.
  변화율의 분모가 0이면 `null`이다. 저장 시점 사이는 값이 유지된 계단형으로만 그리며 중간 값을 추정하지 않는다.
- 기간은 항상 서비스 관측기간(`basis=service_observed`)이다. 광고 최초 게시일을 알 수 없으므로 서비스가 저장하기 전 변화는 모른다.
- 상태 변경은 사용자가 저장한 값 사이의 변화만 보인다. 수집 실패·접근 제한·페이지 미노출(`blocked`·`unavailable` 등)은 거래 완료나 가격 변경으로 해석하지 않고
  `collection`에 시도 횟수·읽음/못 읽음·최근 10건으로만 표시한다.
- 원문을 읽은 시도의 표시 가격이 저장값과 다르면 `differs_from_saved`로 알리기만 한다. 사용자가 확인해 직접 저장하기 전에는 저장값·후보·분석을 바꾸지 않는다.
- 가격 인하 이력은 협상 근거 준비용 참고이며 협상 가능성이나 매도인 사정을 확정하지 않는다. 같은 화면에 실거래·AVM 비교를 겹치는 일은 아직 하지 않았다.

검증: Kotlin 단위 3건(`ListingTimelineTest`)과 실제 Spring·PostgreSQL 통합(`ListingPersistenceIT`의 타임라인·타인 404). 화면은 타입·린트만 통과했으며 브라우저 흐름 검증은 아직 없다.

#### 실거래·AVM 겹쳐 보기 (2026-10-10)

타임라인 패널의 그래프에 저장한 호가 계단선, 같은 단지 실거래 점, 저장된 AVM 마름모를 한 시간축에 겹친다. 조회 중 외부 API·LLM·분석 작업·후보 상태 변경은 없다.

- **대상:** 전용면적 기준(`area_basis=exclusive`)이 확인된 법정동 있는 **아파트 매매**만 연결한다. 그 밖에는 이유를 표시한다.
  공급면적이나 면적 기준 미확인 값을 전용면적처럼 실거래와 맞추지 않는다.
- **실거래:** Spring이 내부 `POST /internal/v1/data/listing-trades`를 호출한다. Python은 이미 저장된 국토부 신고(`transactions`)에서 같은 시군구·같은 법정동(코드가 있는 행)·
  단지명이 일치하는 거래를 최근 24개월·전용면적 ±10%로 고르고 해제·중복·미래 거래를 뺀다. 이름이 여러 단지에 걸리면 연결하지 않고, 부분 일치는 유일할 때만 `partial_unique`로 표시한다.
  저장된 마지막 거래월(`data_through`)을 함께 보여 신고 지연으로 최근 거래가 빠질 수 있음을 알린다.
- **호가 대비:** 최근 6개월 거래가 3건 이상이고 호가·면적이 있을 때만 ㎡당 중앙값 대비 호가 차이(%)를 계산한다. 시점수정·층·향·동 보정은 없으며 적정가격 판단이 아니다.
- **AVM:** 같은 사용자의 후보 중 이 매물에서 만든 후보의 저장된 가격 분석만 읽는다. `market_reference`이고 `comparison_eligible`인 분석만 가격을 표시하고(오래된 분석은 속이 빈 마름모),
  보류·참고용·이전 기록은 가격을 숨기고 건수만 알린다. 실거래 조회 서비스가 실패해도 호가 이력과 저장된 AVM은 계속 보인다.
- 검증: Kotlin 단위 3건(`ListingMarketOverlayTest`), 통합 1건(AVM 표시 기준·조회 실패 후 유지·조회가 저장 상태를 바꾸지 않음·타인 404), Python 3건(`test_listing_trade_overlay.py`),
  실제 저장 거래로 메이플자이(서초 19건)·아남(6건) 연결과 미존재 단지 미연결을 확인했다. 브라우저 화면 검증은 아직 없다.

`/listings`의 ‘매물 원문 불러오기 · 시점 이력’에서 네이버 개별 매물 링크를 조회한다. Playwright Chromium을 백그라운드 작업으로 실행하며 작업 상태는 기존 Redis 작업 관리자에 저장한다. 사용자당 요청 간격은 1분, 브라우저 작업 제한은 45초다.

<a id="listing-collection-사용자-흐름"></a>

### 사용자 흐름

1. 개별 매물 링크 입력 → 원문 수집·재확인.
2. 추출된 가격·전용면적·주소·원문 확인일을 검토한다. 알 수 없는 값은 추측하지 않는다.
3. 추출값을 등록 폼에 적용한다. 부동산 유형은 직접 선택·확인한다.
4. 사용자 확인 일시와 거래 상태를 직접 입력한 뒤 저장한다. 페이지가 보인다는 이유로 거래 가능을 자동 지정하지 않는다.
5. 거래 가능·최근 7일·법정동 연결 조건을 충족한 매매 매물만 후보로 저장한다.

<a id="listing-collection-시점과-상태의-의미"></a>

### 시점과 상태의 의미

| 항목 | 의미 |
|---|---|
| requested_at | 브라우저 조회를 시작한 시각 |
| fetched_at | 해당 조회가 끝난 시각. 실패에도 기록 |
| first_seen_at / last_seen_at | 가격·전용면적을 식별한 최초/마지막 수집 완료 시각 |
| source_confirmed_date | 원문에 표시된 확인일 문자열. 수집 시각으로 대체하지 않음 |
| confirmed_at | 사용자가 검토하여 입력한 확인 시각. 기존 매물 저장 기준 |
| observed | 페이지 표시값을 식별함. 거래 가능 보증이 아님 |
| unavailable | 페이지가 없거나 원문이 종료됨. 거래 완료·철회 여부는 알 수 없음 |
| blocked / failed / parse_error | 접근 제한 / 실행·통신 실패 / 가격·전용면적 식별 실패 |

각 조회 결과는 `listing_observations`에 별도로 남긴다. 조회 실패·원문 없음으로 기존 매물 가격이나 상태를 변경하거나 레코드를 삭제하지 않는다. 가격 변경 전후의 추출값은 수집 이력에, 사용자가 저장한 가격 변경은 기존 `listing_revisions`에 보존된다.

사용자 확인보다 새로운 수집 기록이 있거나 사용자 확인 후 7일이 지나면 ‘재확인 필요’다. 최신 추천과 후보 저장에서 제외되며 사용자가 확인 일시·상태를 다시 저장해야 복귀한다. 보관함 카드의 **다시 확인해 저장**(`POST /api/listings/{id}/confirm`)은 확인 시각·거래 상태·거래 유형에 맞는 가격만 받아 기존 매물을 갱신하고 `listing_revisions`에 새 버전을 남긴다. 이름·주소·면적·동호·주소/건축물 근거는 바꾸지 않으며, 물건이 다르면 새 매물로 등록한다. 저장된 확인 시각보다 같거나 이른 시각은 409, 미래 시각·시간대 없는 시각·잘못된 상태·거래 유형에 맞지 않는 금액은 422, 타인 매물은 404다. CSV를 다시 올리는 경로는 주소·건축물 확인 서명을 다시 요구하므로 단건 재확인에는 이 경로를 쓴다. 연결된 후보에는 기존 원본 변경과 같은 재확인 안내가 표시된다. 7일은 제품의 표시 기준이지 실제 매물 유효기간이 아니다. 이미 저장한 케이스 후보·분석 결과는 당시 스냅샷으로 보존한다. 원본 매물의 가격·주소·면적·거래 상태 등이 바뀌거나 재확인이 필요해지면 후보와 비교 화면에 차이 및 경고를 표시한다.

<a id="listing-collection-현재-범위"></a>

### 현재 범위

개별 링크를 사용자가 요청할 때만 조회한다. 정기 재수집·지역 전체 수집·목록에서 사라진 매물 판정은 없다. 자동화된 접근 제한을 우회하지 않으며 실패하면 수동 확인·등록을 이용한다. 원문 화면 변경이나 식별 불가능한 표기는 `parse_error`로 남는다. 토지·비주거처럼 전용면적이 없는 유형은 현재 자동 추출 성공 조건을 충족하지 못하므로 수동 입력한다.

실행은 Redis Stream과 별도 `job-worker`를 사용한다. 재시작 시 복구 경계는 [운영 문서의 작업 복구](../operations.md#job-recovery)를 따른다. 정기 재수집 정책은 별도다.

실제 네이버의 예전 매물 링크 1건을 Chrome으로 조회했을 때 ‘페이지를 찾을 수 없습니다’를 확인했다. 현재 유효한 실제 매물에서 가격·면적 추출 성공 여부는 아직 확인하지 못했다. 이 상태를 운영 수집 완료나 실매물 데이터 확보로 설명하지 않는다.

<a id="listing-collection-접근-제한-분류와-서비스-공통-대기-2026-09-25"></a>

### 접근 제한 분류와 서비스 공통 대기 (2026-09-25)

네이버 상세는 지도 화면으로 이동한 뒤 내부 API로 매물 정보를 읽는다. 실제 진단에서 내부 API가 429를 반환한 후 HTTP 200 오류 화면으로 이동해 종전 수집기가 `unavailable`로 분류하는 문제를 확인했다.

`naver-dom-v2`는 해당 매물 ID의 핵심 API 또는 문서 요청에서 401/403/429를 관찰하면 최종 오류 화면보다 우선해 `blocked`로 분류한다. 광고·로그인·다른 매물의 API 오류는 이 판단에서 제외한다. `reason_code`, `upstream_status`, `restriction_source`를 수집 기록에 보존하며 가격과 거래 상태를 변경하지 않는다.

Redis의 `listing-collection:naver:next-request` 키로 서비스 전체의 브라우저 실행 간격을 60초 이상 유지한다. API·별도 실행기뿐 아니라 `collect_page()`를 호출하는 평가기도 이 제한을 따른다. 접근 제한 후 최소 900초 대기하며, 서버 `Retry-After`(초 또는 HTTP 날짜)가 더 길면 그 시간을 따른다. 대기 중에는 브라우저를 열지 않으며 자동 재시도하지 않는다. Redis 장애 때도 외부 요청을 진행하지 않는다.

대기 중 API 요청은 HTTP 429와 `Retry-After`를 반환한다. 이미 큐에 들어간 작업은 실행 시 다시 확인해 `blocked`, `reason_code=collection_cooldown`, `request_sent=false`로 종료한다. 이는 새로운 원문을 조회했다는 뜻이 아니다. 프론트는 재시도 가능 시각을 표시하고 수집 버튼을 비활성화하며 수동 등록과 과거 이력 조회를 유지한다. 새로고침 후에도 서버의 공통 제한은 유지된다.

이 대기는 네이버의 접근 제한 해제를 보장하지 않는다. 유효한 실제 매물의 값 대조는 여전히 별도 검증이 필요하다. 여러 정답 링크를 평가할 때도 공통 간격을 지켜 개별 실행하고, 대기 중 건을 수집 성공으로 집계하지 않는다.

### 후보 연결 및 주소 파서 보강

후보 저장은 같은 트랜잭션에서 매물 소유권·거래 상태·확인 시각을 재검사한다. 같은 케이스에 같은 원본 매물을 다시 저장하면 기존 후보를 반환한다. 저장 당시 매물 버전과 핵심 값을 보존하므로 원본을 갱신해도 이전 판단의 희망가가 조용히 바뀌지 않는다. 원본을 지워도 당시 값은 남고 재확인 경고가 표시된다.

상세 페이지에서 `소재지`를 `위치`, `주소`보다 우선하며 중개사무소 구역의 주소는 무시한다. 같은 우선순위의 주소가 충돌하면 자동 입력하지 않는다. 이 파서 보강은 가상 본문으로 검증했으며 현재 유효한 실제 네이버 매물에서의 성공을 뜻하지 않는다.
