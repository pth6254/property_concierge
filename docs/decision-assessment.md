# 후보별 의사결정 검토 기준

매수 케이스의 **매수 검토 요약**에서 후보별 적합성·가격성·자금성·위험성·실행성을 확인한다. 각 축은 사용한 값·출처·기준 시각과 부족한 정보를 보여주고, 해당 입력·분석·검토 화면으로 연결한다. 후보 선택은 사용자가 한다.

## 이용 흐름

1. 매물 보관함에 관심 매물의 URL 또는 직접 확인한 값을 등록하고 매수 케이스에 후보로 저장한다.
2. 케이스에서 예산과 공통 매수 조건을 입력하고 후보별 시세·자금·권리 분석을 실행한다.
3. **매수 검토 요약**에서 후보별 확인 상태와 판단 근거를 비교한다.
4. 다음 행동으로 부족한 입력·서류·현장 확인을 보완한다. 후보 비교에서 선택 이유를 저장하면 거래 준비 작업으로 이어진다.

포털의 매물 추출 성공은 필수 조건이 아니다. 직접 입력한 후보도 검토할 수 있으나 출처·확인 시각을 연결하지 않으면 미확인 사항으로 남는다.

## 판단 축과 표시 기준

| 축 | 사용하는 자료 | 현재 표시 기준 |
|---|---|---|
| 적합성 | 예산, 면적, 물건 유형, 관심 지역의 법정동 코드 | 설정된 조건만 비교한다. 후보의 준공연도가 없으면 연식 조건은 미확인이다. 지역 이름만으로 법정동을 추정하지 않는다. |
| 가격성 | 희망가, 저장된 AVM 추정가·신뢰도·비교사례 수 | 유효한 기준일, 양수 가격, 신뢰도 50% 이상 및 100% 이하, 비교사례가 있을 때 가격 차이를 계산한다. 희망가가 추정가보다 5% 넘게 높으면 재검토를 안내한다. 이 값은 서비스의 확인 기준이며 적정 매수가격이나 정확도 보장이 아니다. |
| 자금성 | 후보 가격과 저장된 계산 결과·입력 조건 | 현재 가격으로 계산했는지, 취득 후 주택 수가 기록됐는지, 현금·첫 달 상환액·소득 등 필요한 기준이 있는지 확인한다. 현금 부족·상환 부담·계산기에 적용된 대출 기준 초과는 주의로 표시한다. |
| 위험성 | 업로드 문서의 판독 결과와 위험 신호, 매물 출처 확인 | 등기부·건축물대장 판독 여부를 업로드 여부와 구분한다. 둘 다 판독되지 않았거나 원본 확인 시각이 없으면 검토 완료로 표시하지 않는다. 과거 위험 신호는 만료 후에도 재확인 대상으로 남긴다. |
| 실행성 | 위 네 축, 체크리스트와 다음 행동, 사용자 선택 기록 | 네 축의 근거와 등록된 확인 항목이 모두 해결된 경우에만 등록 검토 항목 확인으로 표시한다. 체크리스트 완료율을 추천 점수로 사용하지 않는다. |

상태는 `등록 자료 확인`, `주의·재검토`, `미확인`, `갱신 필요`, `분석 실패`, `분석 중`을 구분한다. ‘등록 자료 확인’은 저장된 자료로 해당 기준을 비교할 수 있다는 뜻이며 거래 안전성의 인증이 아니다.

매물 원본 변경·재확인 필요, 분석 만료·기준일 누락·미래 시각, 후보 가격과 자금 분석 가격의 불일치가 있으면 이전 결과를 현재 비교 금액에 사용하지 않는다. 과거 값은 근거에서 이전·미확인 값으로 구분해 볼 수 있다. 기준 시각을 모르는 자료에 조회 시각을 임의로 채우지 않는다.

## 구현 계약

`GET /api/cases/{id}/summary`는 소유자 확인 후 `case`, `comparison`, `decision`을 반환한다. `decision`은 버전·조회 시각·후보별 다섯 축·현재 사용 가능한 비교 금액·다음 행동·결과의 한계를 포함한다. 각 근거의 출처는 사용자 입력·계산 결과·문서 분석·작업 기록으로 구분한다.

`backend/services/case_decision_assessment.py`가 같은 케이스 자료에서 결과를 계산한다. 후보 비교도 이 결과의 검토 완료 여부와 가격 차이를 사용한다. 조회 중 외부 API·LLM·새 작업을 실행하거나 선택 상태를 변경하지 않는다. 별도 테이블이나 데이터 이관 없이 기존 후보·분석·체크리스트를 사용한다.

자금 분석은 후보에 저장된 개별 입력을 사용하며 공통 조건과 다르다는 이유만으로 무효화하지 않는다. 재계산 화면에서는 저장된 입력과 공통 조건 적용을 선택할 수 있다. 권리 원문 PDF는 기존처럼 저장하지 않으며 판독 성공 여부만 요약에 추가한다. 이전 권리 결과에 이 기록이 없으면 다시 분석해야 한다.

## 검증 범위

- `tests/test_case_decision_assessment.py`: 다섯 축의 근거, 상태 구분, 기준일 누락·미래 시각·만료, 원본 변경, 가격 차이, 자금 입력 부족, 판독 실패, 법정동 범위와 자동 선택 방지를 확인한다.
- `tests/test_purchase_cases.py`: 실제 API의 소유자 격리, 조회 후 상태 보존, 판독할 수 없는 PDF의 확인 상태를 검증한다.
- `evaluation/datasets/decision.json`: 고정 시각의 가상 케이스를 재생한다. 비교사례 수·문서 판독·취득 후 주택 수·매물 확인 시각은 선언된 검증용 입력이며 실제 매물 또는 문서 판독 실적이 아니다.
- `scripts/verify_decision_assessment_browser.cjs`: 실제 자금 계산·후보 저장, 다섯 축 표시·근거 확인, 조건 전달, 가격 수정 후 재검토, 새로고침 복원, 미확인 상태에서 사용자 선택, 좁은 웹 화면을 확인하고 임시 계정을 삭제한다.

브라우저 결과는 `evaluation-results/assessment-browser*.json`과 화면 이미지에 저장한다. CI에도 이 흐름과 아티팩트 보관을 추가했다. 실행 중인 서비스에는 `node scripts/verify_decision_assessment_browser.cjs`, 개발 프론트엔드를 따로 띄울 때는 명령 뒤에 API 주소를 전달한다.

2026년 10월 1일 격리 DB·Redis에서 백엔드 전체 테스트 1,065건이 통과했고 1건은 건너뛰었다. 프론트엔드 타입·린트·프로덕션 빌드와 Docker 재빌드가 통과했다. 실제 Docker 서비스와 로컬 개발 프론트엔드에서 통합 의사결정 브라우저 검증 13개 항목이 각각 통과했으며 임시 계정 삭제 응답은 모두 200이었다. 기존 자금 브라우저 검증 13개 항목과 화면 이동 검증 7개 항목도 통과했다. 로컬 개발 프론트엔드 검증은 로컬 API에 연결했으며 원격 GitHub Actions 실행 완료를 의미하지 않는다.

이 검증은 저장된 근거를 올바르게 연결하고 불확실성을 표시하는지 확인한다. 실제 AVM 정확도, 문서 위험 신호 탐지 정확도, 실호가·매물 존재, 최신 세금·금융 규칙의 전체 예외, 사용자 투자 성과를 보장하지 않는다. 통근·학군·소음·주차 자료, 문서 발급일·페이지별 근거와 부동산 객체의 완전한 동일성은 후속 작업이다. 모바일 앱 개발은 이후 단계로 둔다.
